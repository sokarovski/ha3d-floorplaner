# Frontend architecture and code placement

Updated: 2026-11-19. Earlier: 2026-11-17 (Phase 11 production host).

Status: D13 is resolved. The route/module layout, React Router Data Mode, Zustand, and typed client/service/domain/repository boundaries below are the selected MVP conventions. The map and source layout describe the folders that exist (checked 2026-11-16); concrete schemas and method signatures live in the source.

## Responsibility map

| Concern | Proposed home | Rules |
| --- | --- | --- |
| Startup and composition | `src/app/` | Construct router, service clients, stores, and runtime adapters; connect dependencies explicitly |
| Route registration and URL builders | `src/app/routes/` | One explicit route tree, route IDs, parameter validation, and typed link helpers |
| Feature pages/components/hooks | `src/features/<feature>/` | Feature UI and React adapters; pages compose components and invoke use cases |
| Client use cases/services | `src/features/<feature>/services/` | Coordinate loading/saving, domain commands, stores, and resource clients |
| Browser agent adapter | `src/features/floor-builder/automation/`, `src/features/houses/automation/` | [Documented window tools](browser-automation.md), schemas, registry, and agent guides; delegate to the existing session and resource clients. The Houses-level bridge reuses the editor bridge's `bridgeCore.ts` helpers |
| Client stores/selectors | `src/features/<feature>/stores/` | Hold the owned state and expose narrow selectors/actions; no geometry or transport algorithms |
| HTTP transport and resource clients | `src/api/` | HTTP mechanics, runtime decoding, DTO mapping, resource calls, and normalized errors |
| Domain/business rules | `shared/domain/` | Pure typed commands, entities, validation, templates, units, and domain invariants reusable outside React |
| Geometry generation | `shared/geometry/` | Geometry algorithms and adapters without React, HTTP, or filesystem dependencies |
| Object type schemas | `shared/domain/schemas/` | One JSON Schema per object type with `x-homeplan` annotations; used by the panel, commands, and server ([property system](../builder/property-system.md)) |
| Shared transport contracts | `shared/contracts/` | Request/response schemas, revision/error types, and boundary validation contracts |
| Rendering runtime | `src/renderer/` | Scene resources, picking, previews, camera/frame lifecycle, and typed document adapters. Framework-free (Three.js and `shared/` only, no React or stores), so the [HA viewer](../home-assistant/viewer-mvp.md) reuses it ([D23](../decisions.md#d23-ha-viewer-mvp)) |
| Viewport host and playground | `src/features/viewport/` | The React `ViewportHost` that mounts the runtime, and the `/ds/viewport` playground with its fixture house |
| Reusable UI | `src/design-system/` | Shared typed components, tokens, `.tw.css`; no house-store or API dependencies |
| Documentation UI | `src/features/design-system-docs/` | `/ds` pages, typed catalog, example components, and source-dialog content |
| General utilities | `src/utils/` (not created yet) | Small domain-neutral helpers; no React hooks, stores, HTTP, or application workflows |
| Backend routes/services | `server/routes/`, `server/services/` (routes per [API specification](api.md)) | Validate requests/resources, run server use cases, enforce write/concurrency policy |
| Filesystem repositories | `server/repositories/` | Implement model/asset/preferences storage operations behind typed interfaces |
| Backend helpers | `server/http/`, `server/templates/`, `server/render/`, `server/builtin-templates/`, `server/builtin-materials/` | Error envelope, multipart and schema compilers; glTF/STL normalization; the Blender render adapter and job queue; the built-in template files; the built-in texture images (generated by `npm run materials:build`) |
| HA viewer | `ha-viewer/` | The separate Lit front end ([D23](../decisions.md#d23-ha-viewer-mvp)); imports only `shared/` and `src/renderer/` (ESLint-enforced). The React, Tailwind, React Aria, `SchemaForm`, and `/ds` rules do not apply there |

The feature folders are `houses`, `floor-builder`, `object-editor`, `preferences`, `design-system-docs`, `viewport`, `forms` (shared form-submit error mapping), and `not-found`. Keep feature-only helpers with their feature. Shared dimensions or wall rules belong to the domain, not to a generic `utils` dumping ground.

**HA production host:** a Python integration provides a stable packaged loader/recovery shell and a separate production viewer bundle; [production integration](../home-assistant/production-integration.md) owns the layout/lifecycle. One saved URL and DEV MODE in House setup select remote code plus working house data together; off/fallback uses compatible local UI and stored house. Native Configure recovers this same record. Per-house Upgrade and Upgrade panel store verified immutable local resources; code switching needs browser reload while normal selection updates the scene/sidebar reactively. No frontend-owned duplicate mode/store or HA/React/store imports enter the framework-free renderer. The component is distributed through Marketplace and as a release ZIP ([distribution and builds](../home-assistant/production-integration.md#distribution-and-builds)).

## Routing conventions

Use React Router Data Mode in the Vite SPA: explicit route objects registered outside React rendering, with lazy page modules, nested layouts, loaders where useful, pending/error boundaries, and navigation blocking for unresolved edits. This retains control over the separate Node API and shared editor state. [React Router modes](https://reactrouter.com/start/modes).

Create the router once in app composition. Route-definition modules contain configuration/functions, not inline component definitions. Pages are named arrow-function components in their own files and are referenced by import/lazy import. Loader/action functions delegate to feature services/resource clients; they do not contain wall rules or direct `fetch` calls.

| Logical route | Responsibility |
| --- | --- |
| `/` | Houses page |
| `/houses/:houseId` | Floor Builder house context |
| `/houses/:houseId/objects/new` | New object-template authoring draft (the `:templateId` route with the reserved value `new`, which shows the Import model popup) |
| `/houses/:houseId/objects/:templateId` | Existing template authoring |
| `/ds/*` | [Design-system documentation](../design-system/workbench.md), including `/ds/viewport` |
| Unmatched route | Not-found page with navigation back to a valid context |

The listed logical routes are the selected MVP route convention, including the required `/ds` documentation. The route modules are `houseRoutes.ts` and `designSystemRoutes.ts`; every page is a lazy import. Initial editor mode, active tool, and temporary selection remain session state. Add explicit URL/query parameters later if shareable floor/mode navigation is needed; do not maintain two writable authorities for the same navigation value.

`paths.ts` owns URL construction and segment encoding. Validate route parameters before use; IDs identify resources and are not filesystem paths. Use router links/navigation so the SPA keeps its lifecycle and deployment prefix. Register `/ds` separately from visible product navigation metadata.

Router `basename` and API/asset base URLs come from one validated runtime configuration and may have different values. Resolve them explicitly; a leading `/api` must not accidentally bypass an ingress prefix. Deep links need SPA fallback, while missing API/assets retain API/asset errors. [Router basename](https://reactrouter.com/api/data-routers/createBrowserRouter).

## Utilities business logic and repositories

Place a function by what it owns, rather than by whether it is a function:

- General formatting/collection helpers with no product knowledge: `src/utils/<purpose>.ts`.
- Length parsing/conversion or template constraints: `shared/domain/units/` or the relevant domain module.
- Wall resize and opening validation: a typed domain command/validator; geometry regeneration belongs to `shared/geometry/`.
- Save the house document and reconcile acknowledgment: the floor-builder service, calling `houseClient` and its store.
- Read/write `house.json`: a backend repository, used by a backend service applying revision/serialization rules.
- Subscribe React to selected values: a feature hook; hooks are not general utilities.

The browser resource client is the HTTP boundary. Do not add a second frontend “repository” that merely renames the same calls. A separate frontend repository abstraction is justified only when a real alternative data source/offline strategy requires one. The backend repository abstracts filesystem persistence, not business policy.

## Dependency direction

Domain/contracts/geometry do not import React, Zustand, router APIs, feature UI, or server modules. The Three.js adapter may depend on the shared geometry core, but shared geometry must not depend on the browser runtime. Backend repositories never enter a browser dependency graph. Design-system components receive props/events and do not import feature services or stores.

App composition injects a small typed service set into route loaders and editor sessions. Services call resource clients and domain commands; stores expose subscriptions/actions; React uses feature hooks. Avoid a global service locator, undocumented `window` state, or a context provider for every dependency. The owner-approved [browser automation bridge](browser-automation.md) is a documented public adapter on `window.homeplan`, not access to raw services or stores. A single stable session reference can be passed through props or a narrow provider when needed.

Keep three distinct layers: a user operation is a **command/use case**, an HTTP call is a **resource-client method**, and a persisted operation is a **repository method**. They may share a purpose but own different validation and failure boundaries. Exact methods/contracts must be added to the specification and types when a workflow is implemented.

## Contributor and model workflow

Before adding code, read this map, [state/data flow](state-and-data.md), the owning feature spec, and [D13](../decisions.md#d13-application-stack). Inspect actual source before importing a named module: proposed paths in a spec are not proof that an implementation exists.

For each change, identify its route/UI entry, state owner, domain command, client/server contract, and persisted data. Reuse an existing implementation at that layer. If a contract is missing, make the smallest explicit proposal/update rather than inventing an unrelated convention or silently changing a required rule.

Document new routes and resource methods with their feature; document shared components in `/ds`; keep props metadata/examples with the implementation change. Update this map if adopting a different framework/layout. ESLint's `no-restricted-imports` enforces the layering: `shared/` imports no React, stores, Three.js, or server code; `src/design-system/` imports no features, API, renderer, or stores; browser code imports no server code; `ha-viewer/` imports only `shared/` and `src/renderer/`.
