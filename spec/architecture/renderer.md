# React and Three.js integration

Updated: 2026-11-16.

Status: D13 is resolved. MVP uses a typed Three.js runtime hosted by a small React viewport component, with Zustand subscriptions and the shared document/command layer. React Three Fiber is not selected. Since [D23](../decisions.md#d23-ha-viewer-mvp), `src/renderer/` is also used by the Lit [HA viewer](../home-assistant/viewer-mvp.md), so it must stay free of React, stores, and design-system imports (owner requirement, AGENTS.md).

## Alternatives considered

| Approach | How it works | Main tradeoff |
| --- | --- | --- |
| React Three Fiber | Describe the scene with React components; Fiber manages Three.js object creation/lifecycle, with imperative frame updates where appropriate | Useful declarative composition and ecosystem, with React/Fiber compatibility requirements |
| React-hosted Three.js runtime | React mounts a viewport; a plain TypeScript runtime owns the Three.js scene and synchronizes it with shared application data | Explicit scene/lifecycle management and more adapter code, with a rendering core reusable outside React |

React Three Fiber is itself a React renderer for Three.js. It does not require routing every animation or pointer movement through React state: its documentation recommends imperative updates for high-frequency operations. Neither approach inherently implies rebuilding the scene for each frame. [Fiber introduction](https://r3f.docs.pmnd.rs/getting-started/introduction), [Fiber performance guidance](https://r3f.docs.pmnd.rs/advanced/pitfalls).

## Selected boundary

For this editor, use a **Three.js rendering runtime mounted inside React**, driven by shared typed document data and editor commands.

Reasons for the selection are the existing abstract JSON/template model, custom geometry operations, multiple editor tools, image/geometry export paths, and the intended reuse of rendering in Home Assistant cards. These are architectural considerations, not a demonstrated performance advantage over Fiber.

This is an in-page canvas/runtime. It does not require an iframe, another application, JavaScript without types, or a worker. It also does not move GPU or CPU work off the main thread automatically.

## Responsibilities

| Layer | Owns |
| --- | --- |
| React interface | Layout, toolbox, overview tree, property forms, menus, and settings |
| Shared document/editor layer | Authoritative house/floor/area/object data, stable IDs, selection/tool context, validation, edit commands, and persistence coordination |
| Geometry/template core | Footprints, wall/opening geometry, the roof's wall limit (clipping, walls rising, the window limit), stair templates, floor cuts (`floorCuts.ts`), and asset normalization |
| Three.js runtime | Scene graph, meshes/materials/lights, cameras, canvas rendering, picking, tool previews, and GPU resources |
| Small React viewport host | Mount/unmount the runtime, size its host, and connect typed data/commands/events |

React edits the same document model that drives the renderer; the house model is not required to live inside React component state. Use explicit subscriptions/adapters without a large provider hierarchy. Live Three.js meshes and cameras are runtime resources, not values serialized into `house.json`.

MVP rendering takes one active building-floor snapshot at a time, together with its inherited house environment and required assets. Other floors contribute no geometry, emitters, shadows, or picking targets. A floor switch replaces the scene and rejects stale work from the previous floor. House-wide metadata/state can remain loaded without constructing a vertically stacked scene. **Exception, the HA whole-house view** (Phase 16.1, [viewer MVP](../home-assistant/viewer-mvp.md#floors-and-the-whole-house)): `houseExterior.ts` stacks every floor complete (Phase 18.1: shell, textures, carpets, furniture, stairs, real doors and windows, wall-mounted items, trees, fences, light fixtures; one lights layer lights every floor's lamps; no effects) at its placement, as a read-only exterior floor selector, merged per floor once settled ([house exterior](#house-exterior)); the HA floor switch (16.3, 16.13) draws a copy of the departing view (its meshes and own lights, sharing geometry and materials, in a separate scene at its real position relative to the destination, `ha-viewer/three/floorGhost.ts`) blended over the destination with weight 1 − the ride's progress while the camera rides vertically between the two (then a separate fit move), released when the ride ends; the destination's scene never contains the other floor.

Apply the [editor camera/view rules](../builder/screens/floor-builder.md#camera-controls-and-view-choices): centered orbit/pan/zoom in the main view, locked Top versus rotatable 3D floor layout, and unified Room Editor with Top/3D views and automatic 3D on wall-tool selection. Camera orientation is runtime/editor state, separate from persisted model axes and object transforms. Edge-drag and camera gestures must not compete for the same active pointer operation.

The geometry core prepares [RealAllWalls](../builder/features/shared-walls.md) before the runtime consumes it: union clashing walls, omit contact faces, and retain material/source references. Optional mesh batching follows this step. The runtime renders RealAllWalls only, never the individual RealWalls on top of it, and picking maps faces back to authored walls.

[Geometry groups](../builder/features/geometry-groups.md) preserve local child geometry and compose parent transforms. The geometry core derives RealFloor from the floor shape and the walls, and builds RealAllWalls by merging each wall's RealWall. Render RealFloor and RealAllWalls once; RealWalls serve picking and highlights, and source shapes are editing helpers when shown. Keep canonical lengths in millimeters and convert only at the renderer boundary. Derived Three.js objects are never a second saved model.

The [state/data design](state-and-data.md) supplies a concrete implementation: one Zustand-backed editable document store per house session, narrow React selector hooks, and direct runtime subscriptions. Domain commands remain independent of Zustand. [Frontend architecture](frontend-architecture.md) owns source placement and routing. The comparison above is rationale, not an open MVP integration choice.

## Data flow and interaction example

Changing a wall's thickness in the React properties panel sends an edit command to the document layer. After validation, the model changes; the scene adapter updates the affected wall, openings, and dependent floor support. Other geometry remains reusable.

Clicking an object in the canvas produces its stable object ID. The editor selection model changes, and React displays that object's properties and relevant tools. The renderer does not directly manipulate React panel DOM.

During a drag, the runtime can show a temporary high-frequency transform/geometry preview. Publish live values to the properties UI at an appropriate cadence, and commit one authoritative model transaction when the operation completes. Cancellation restores the committed state without history. [Undo/redo](../builder/undo-redo.md) restores authored values and regenerates derived resources; there must not be two competing saved house models.

Keep camera motion, hover previews, and animation outside React's component render cycle. Changes in forms and selection should update the affected interface normally; do not serialize or replace the entire house/scene on every pointer movement.

Viewport pointer input includes distinct `down`, `move`, `up`, `leave`, and `cancel` phases. Pointer cancellation and unexpected capture loss emit `cancel`; an ordinary leave is separate. Camera gestures stay outside editor pointer input. The feature-owned tool pointer adapter implements [automatic click/drag detection and Auto-select](../builder/screens/floor-builder.md#operation-input-click-lock-type-commit); the renderer only forwards screen coordinates, buttons/modifiers, plan intersections, and picks.

## Proposed runtime boundary

A minimal typed adapter can expose:

- Mount/initialize and dispose lifecycle.
- Initial scene snapshot and incremental document-change application.
- Active tool, selection, and focus/isolation updates.
- Walls off (`setWallsVisible`, Phase 4.5): wall meshes are replaced by flat floor-level traces of the wall footprint and wall openings (Wallable doors and windows) are hidden with them; wall-attached Areable objects stay drawn and pickable in place (owner, 2026-11-17; `InstanceLayer.setWallOpeningsVisible` decides by contract, Wallable vs Areable); PNG and render exports always include the walls.
- Viewport resize and render invalidation.
- Preview/image export entry points using immutable render snapshots.
- Typed events for selection, tool previews, and completed edit requests.
- `doubleClick` events carry viewport-local screen coordinates and the picked hit (or null), including faded rooms excluded from ordinary selection. The host decides whether to enter Room Editor, exit it, or frame empty space in overview; the runtime does not frame independently.

The document layer remains responsible for validating and applying edit requests. The runtime updates its derived scene by stable IDs, with explicit geometry/material/resource ownership. Async asset loading or geometry work must not apply stale results after a newer edit or scene switch.

Shared geometry, template logic, and the scene layers are reused by another host: the HA viewer ([D23](../decisions.md#d23-ha-viewer-mvp)). Host-specific editor tools, HTML panels, and card action bindings remain separate. A shared rendering core does not require cards to adopt the builder's React UI.

### Builder house overview

Phase 16.4 (owner 2026-11-18). `setHouseOverview(true)` draws every floor of the scene's house stacked at its placement through `houseOverviewLayer.ts` and releases the single-floor content (floor scene, instances, lights, effects, guides sync to no floor), so entering a floor afterwards builds only that floor in its local frame and the other floors leave the live scene. While it is on, model-facing values (picks, `planPointAt`, overlays, framing bounds) are in the house frame, a pick is `{ kind: "buildingFloor", floorId, pointMm }`, Fit frames all floors, and the sun's shadow box fits the whole house. A running floor move calls `setFloorPreviewOffsets` (extra offsets by floor ID), which only moves the floors' roots: nothing is rebuilt while dragging, and the commit re-syncs only the moved floors. Walls off and the visibility rule (Hide/Hidden) apply per floor as in a floor view.

**Detail policy** (Phase 18.1, owner 2026-11-18, replacing the 16.4 cost choice): every floor is shown complete, like a floor view: room floors, carpets, RealAllWalls, slab, textures, and all of its content (furniture, stairs, doors and windows, wall-mounted items, trees, fences, light fixtures) through one instance layer per floor, and every floor's lamps through the runtime's one lights layer (`contentFloors`, `areaGroup`, `emitters`: one light topology, the house shadow budget `houseShadowBudget` = 4; light pins are hidden in the overview and never picked, since a pick there is a floor). Ambient effects are not drawn there. Hidden lights keep shining without their fixture, as in a floor view. A floor move preview moves only the floors' roots; the content, its lights and its batch live under them, so nothing is rebuilt while dragging. Once settled (300 ms after the last sync, one floor per 50 ms step), each floor is merged (`staticBatch.ts`, as in the [house exterior](#house-exterior)); a sync, Walls off, fixture visibility or a material change that no longer matches drops that floor's batch at once. Measured on the demo Family house (`?homeplanTiming`, desktop Chrome, 2026-11-18): syncs 0.2–37 ms (37 ms when a template batch arrives), merging 17–44 ms per floor (3998 meshes in 370 draws), then 675 draw calls a frame and a 9.9 ms average render (CPU side, the 60-frame log `frames: render avg`).

### House exterior

Phase 16.1, completed in Phase 18.1 (owner: the whole house shows every floor complete), `houseExterior.ts`, hosted by the HA viewer ([viewer MVP: complete floors](../home-assistant/viewer-mvp.md#complete-floors-in-the-whole-house)). Each floor is its floor scene plus an instance layer over the host's (staged, gated) template cache, in a group at its placement; the host lights every floor with its one lights layer and syncs content with the floors' live states. Floors are kept by ID and the floor scene memoizes by the floor value, so syncing the same house again rebuilds nothing; the HA viewer keeps the exterior hidden while a floor is shown. A hidden exterior's walls are left out of the linear lights' wall probes (lightsLayer.ts probes only drawn walls).

**Static batching** (`staticBatch.ts`): a complete floor is thousands of meshes, and a whole-house frame's cost is its draw calls (about 10 µs each on desktop Chrome, independent of the pixel count: a quarter resolution saved 5 %). Once a floor has settled, its drawn opaque single-material meshes on the model layer alone are merged into one mesh per material, attribute layout, index presence and shadow flags (so the merged mesh uses the same shader program), in the floor's own frame (mirrored sources keep their winding), sorted into buckets by `floorBatchBuckets`: light fixtures stay unmerged (their glow follows their light), objects go to "objects" (the HA viewer hides that bucket from its glass reflection like the objects), the rest to "house". Meshes with their own picking or render hook (shadow-only ceilings) and transparent or multi-material meshes stay as they are. The sources move to layer 30, which no camera renders; Three.js's shadow passes follow the camera's layers, so they skip them too. The merged meshes share the source materials, so texture maps that arrive later apply. A batch is checked after every content sync and material pass (`valid`: every source still drawn with the same material and geometry, no new mesh to draw) and dropped at once when stale, until the host merges it again.

### Roofs

Phase 19.1 (owner decision 4; [roofs](../builder/features/roofs.md#where-roofs-are-drawn)). `roofLayer.ts` (framework-free) draws a floor's roofs from `shared/geometry/roofMesh.ts` in the floor's frame, one group per roof (`roof:<id>`: top, underside, edge, ribs meshes in their materials), casting and receiving shadows, memoized by the roof value. It is used in three places only: inside each floor's group of the house exterior (HA whole house) and of the builder house overview (so a floor move moves it), and by the viewport runtime for a roof's editing level (`setRoofView(roofId)`: that roof over the open floor, picks hitting it are `{ kind: "roof", roofId, floorId, pointMm }`). Floor and room views never draw roofs; their walls are still clipped by and risen to the roof (Phase 19.2), because that happens in `shared/geometry/realAllWalls.ts` (`roofLimit.ts`, `roofClip.ts`), which the floor scene and the HA viewer use unchanged. In the whole-house views a roof merges into its own static-batch bucket `roof:<id>`, so a pick on the merged mesh still names it (the builder overview resolves it to a `roof` hit, the HA viewer to the roof's floor); bounds and framing points reach the roof's top and overhang.

Phase 19.3: the roof meshes are cut by the roof's holes and roof windows (`shared/geometry/roofOpenings.ts`; lining bands, clipped ribs) and carry step faces (side material, or a `stepWall` mesh in the plain wall paint). Each roof window that fits is drawn by `roofLayer.ts` from its roof-window template (resized like any Wallable: `widthMm`, `heightMm`, the slab thickness across the slope as host depth) inside the roof's group, its matrix taking template x/y/z to the face's level, up-slope and normal axes; without a template source (checks) or before it loads, a plain frame and glass stand in, and `refresh()` rebuilds windows whose template state changed (hosts call it on template loads). `RoofLayer.sync(floor, which)` takes a filter: floor and room views (the builder's viewport runtime and the HA viewer's floor view) draw `attachedRoofsOnly` (canopies, Cuts walls off; a proposal for the owner to confirm), the roof level only the open roof. A builder floor view picks a canopy when nothing of the floor is in front of it (a `roof` hit). The roof face view uses `setFaceView` with a `tilt` (a sloped plane: centre, normal, along and up axes); the camera rig derives its polar angle from the normal (π/2 for a wall, just short of straight down for a flat face) and `facePointAt` measures along and up the tilted plane.

Phase 19.5: line ribs (along break and fold lines) put their sides' tops on the underside of the face each side lies under (no gap under a valley rib). Wall step faces (`roofClip.ts` `stepFaces`) cover step lines too: where two pieces meet with different undersides inside the walls' footprint, a vertical cap-material face from the lower underside to the higher one. Canopies (attached roofs) stay drawn in floor and room views (owner decision 2, 2026-11-19, no longer a proposal); the HA viewer keeps them out of its pick list (taps pass through to the floor) and out of the floor's bounds (camera framing, shadow fit and focus frame the rooms only; a canopy beyond the rooms may lie at the view's edge). **Wide overlay lines:** an overlay `segment` or `polyline` may carry `widthPx` (CSS px); above 1 it is drawn as a screen-space `LineSegments2` with a `LineMaterial` from the helper materials (`wideLine`, cached per tone, dash and width, its resolution set from the viewport's size, dashes kept in screen pixels like the thin lines); the roof overlays use it (3 px lines, 2 px folds and items, 4 px selected items).

**Shadow-only ceilings under a roof** (19.3 fix, `floorScene.ts`, `shared/geometry/roofCeiling.ts`): a room's invisible ceiling (Phase 15.5) under a cutting roof follows min(ceiling height, underside) per roof piece, so it never pokes up through the slopes and shades the roof's top (the demo attic's soft darker band along the eaves). The ceiling mesh is the patches' fills lifted onto their planes (`regionFillOnPlanes`); outside the roof, and on floors without a cutting roof, it is the flat fill as before. No shadow bias, map size, daylight gain or sky constant changed.

## Lifecycle and performance rules

- Initialize the runtime after the viewport host mounts; dispose it on unmount. React documents Effects as the synchronization boundary for external systems/widgets. [React Effect documentation](https://react.dev/reference/react/useEffect).
- Tolerate development setup/cleanup/remount checks without duplicate canvases, listeners, or render loops.
- Keep resources stable across ordinary React rerenders. Detach listeners, stop loops, cancel/ignore obsolete work, and dispose owned GPU resources on teardown.
- Update changed geometry and dependencies rather than rebuilding every floor for unrelated edits. Cache/share appropriate assets with explicit ownership.
- Prefer rendering on invalidation while idle; continue frames when interaction, animation, or progressive rendering requires them.
- **One scheduler per viewport** (Phase 15.3, `frameScheduler.ts`, framework-free, clock and frame source injected): `invalidate()` requests one frame and coalesces every request until it runs; `start({ channel, step })` adds an animation that is stepped with the frame's time in every frame until its step returns false (completed), it is cancelled, or its step throws (cancelled and reported; the loop and the other animations go on). Frames continue while any animation is active or something invalidated during the frame, and stop otherwise, so there is no idle rendering. `cancelChannel` stops one channel only, and `whenIdle(channels, listener)` fires after the frame in which those channels became idle, ignoring other channels. The HA viewer runs every frame through it: the camera spring move (`camera`), all object-state animations (`states`, one animation stepping every pose), and staged asset work (`assets`); ambient effects, presence sweeps, and the tap highlight keep their own timers and only invalidate. Grabbing the view stops only the camera move's camera part (its frame insets spring on), never another channel. A new animation or change after idle wakes a frame; dispose cancels everything and drops the requested frame, and a house or floor change cancels the state animation. Elapsed time is the frame clock: a background tab gets no frames, and on return a state animation ends on its first frame (it is timed absolutely), a camera spring continues (at most 50 ms per step). `npm run frames:check` checks this on a fake clock (an orbit drag during a door animation, two animations with one cancelled or failing, the idle signal beside recurring work, a hidden tab, disposal). **Finding (15.3):** the effects layer restarted its timer on every `schedule()`, and the HA viewer's glass reflection calls `setShown` twice inside every rendered frame, so while frames ran continuously (an orbit, a camera spring, a door animation) the timer kept being pushed past each tick: at 120 Hz an AC's swirl stood still on one frame (0 of 23 ticks in 3 s in the check; 17 of 23 at 60 Hz). `schedule()` is now idempotent (a timer due no later than the next tick is kept) and `setShown` keeps the timer through the reflection's momentary hide.
- Shadow maps are static (Phase 7.10): `shadowMap.autoUpdate` is off and a host requests one shadow update (`shadowMap.needsUpdate`) whenever scene content, lights, isolation, the sun, or export visibility change. Camera-only frames (orbit, pan, zoom, resize, hover, pins, tool overlays) reuse the maps. The HA viewer follows the same rule in its own loop.
- **Stable light topology** (Phase 16.6, [lighting](../builder/features/lighting.md#stable-light-topology-phase-166)): switching, dimming, or recolouring a light never changes what materials compile for. Off emitters stay in the scene at intensity 0, a fixed number of emitters cast shadows, and strip slots follow the floor's strips. Only adding or removing lights, switching floors, or (over the shadow budget) moving the point/spot shadow split changes it. Per light, `shadow.autoUpdate` follows on/off, so off lights skip the shadow pass. The HA viewer recompiles the scene in the background when loading is done (`compileAsync`, with the neighbouring shadow splits); `npm run lights:topology` checks the rule.
- **Off screen, nothing runs** (Phase 16.11, owner 2026-11-18; `viewportVisibility.ts`, framework-free, browser only): a viewport is off screen while the page is hidden (another browser tab, the HA app in the background), while its canvas is not in the document, hidden (another HA panel or dashboard), or out of view (`IntersectionObserver`). Meanwhile the HA viewer's scheduler is paused (`setPaused`: no frame is requested, stepped, or drawn; active animations wait) and the ambient-effect and presence-sweep timers stop; the builder's runtime holds back its redraws and stops its effects' timer. HA state changes still update the model. On return one frame always draws the current state (also when the page loaded hidden), and animations continue on the frame clock as after a background tab (a state animation that would have finished ends on that frame; a camera spring continues). Loading continues off screen without drawing. `npm run frames:check` checks pause and resume on the fake clock. The HA floor switch's slide (16.3, `ha-viewer/three/floorTransition.ts`) is one animation on the `floor` channel that settles exactly once (completed, finished early by a new switch or a resize, cancelled by disposal or a failing step); off screen it waits and ends on the first frame back; the opening watch waits for it like the camera; only the camera moves between the two views (`slidePose`), not the floors, so static shadow maps stay valid during it.
- Ambient effects ([ambient effects](../builder/features/ambient-effects.md#rendering)) are timed by their own timer: it wakes only while an effect runs (8 frames per second for 3.5 s every 20 s) and each step requests a camera-only frame, so effects never redraw the shadow maps; nothing runs between runs, and `prefers-reduced-motion` shows a still frame. Rescheduling keeps a timer that is already due no later than the next tick (Phase 15.3), so frequent frames never starve it.
- Heavy geometry computation may later use workers behind the typed geometry boundary. The initial architecture must not claim worker isolation merely because Three.js is outside React.

The host component follows the [design-system React conventions](../design-system/README.md): one named typed arrow-function component per file. The runtime and geometry core are ordinary typed `.ts` modules; they are not React components and do not need `.tsx` wrappers for each mesh.

**Planned strip performance work:** a proposal covers effective-value comparison, stable light resources and per-light shadow invalidation in both hosts, then measurements; the owner's 2026-11-18 decision already replaced the fill row with the analytic [strip term](../builder/features/lighting.md#strip-light-phase-154) (implemented). The [lighting design](../builder/features/lighting.md#planned-led-strip-performance-phase-12) owns the proposed invalidation table and visual constraints. Current global dirtying above remains the implemented behavior; no new runtime API, profiler or optimization exists merely because it is planned.

## Asset loading

**Never black (Phase 15.1):** a surface material (`materialCache.ts`) takes its image map only once the texture cache reports the image ready (decoded and, with staged loading, uploaded); until then it draws its base colour, tinted by the image's average colour when one is known (`textureCache.ts` computes it at decode; a host may remember it between visits through `SwatchMemory`). Before, the map was set at once and sampled an empty texture, which WebGL draws black, until the image arrived: objects with house-image material overrides (and textured floors) were black at first. Template glTF materials carry no images in current houses (GLTFLoader waits for embedded images before it creates a material anyway). Both hosts get this; the builder otherwise keeps loading on request.

**Staged loading (opt-in; the HA viewer):** `createTemplateCache(…, { queue, laneOf })` and `createTextureCache(…, { queue, lane, prepare, swatches })` send their requests through a `loadQueue.ts` queue instead of loading on the first request. The queue runs at most `concurrency` jobs (the HA viewer: 3); lane 0 is open from the start and the host opens later lanes when their stage begins; the lowest open lane runs first. A job covers the whole preparation, so a slot frees only when the asset is ready. With staged loading, images decode off the main thread through `ImageBitmapLoader` (`createImageBitmap`, flipped at decode so the textures keep `flipY` off and sample as before; TextureLoader where unsupported) and the host's `prepare` uploads each image once (`renderer.initTexture` on a base texture with the users' upload parameters, so every material's texture shares that one GPU upload); `createMaterialCache(textures, { beforeMap })` lets the host compile the mapped shader in the background before the map goes on. `TemplateCache.peek` reads a state without requesting a load. The HA viewer's stages and conventions are in [viewer MVP: loading](../home-assistant/viewer-mvp.md#loading-and-the-opening-sequence).
