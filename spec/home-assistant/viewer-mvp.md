# HA viewer MVP

Updated: 2026-11-18 (Phase 16.1/16.3 whole house, floor switching and transitions; Phase 13.7 floor widgets). Earlier: 2026-11-17 (Phase 11 production component; standalone dev behavior retained).

Status: **owner requirement**, decided in [D23](../decisions.md#d23-ha-viewer-mvp). This is the first Home Assistant deliverable. It is a proof of concept that runs alongside the builder MVP and does not change the builder's own MVP gates. The rest of `home-assistant/` stays future design context.

**Production component delivered:** the [production integration](production-integration.md) implements the gradient-only first screen with **Setup your home**, House setup with one URL/Connect/house list, reactive Use this house/sidebar settings, **one DEV MODE for both remote viewer code and working house data**, visible local fallback, per-house **Upgrade** and **Upgrade panel**. Disabling DEV MODE uses HA-hosted local code and the selected stored house after full browser reload. Bindings/dashboard/settings stay in HA. The instructions below continue to describe the separate standalone dev harness; install the integration using its [packaged instructions](../../custom_components/homeplan/README.md).

## Goal

Show a Homeplan house inside Home Assistant as a full-screen panel. The house sits in 3D on a light-gray rounded dome, like a car on a Tesla display, and you rotate it by dragging. A small overlay shows the live state of one Home Assistant entity as text. That proves both halves of the system: the house loads from the builder, and HA state is reactive without re-rendering the whole view.

The visual style will be revised in viewer MVP 2.

## In scope

- One `panel_custom` entry in `configuration.yaml` loads the panel module.
- **Dev mode only:** the module and the house both come from the Vite dev server on the builder machine.
- A **house picker**: in the standalone harness, shown when no house is chosen yet. In the HA integration, houses are chosen in Settings → **House** → House setup (**Use this house** beside each house); **Swap house** was removed (owner, 2026-11-17). (The first version also picked a test entity; removed 2026-11-16.)
- A **viewer screen**: a one-floor house's floor, or for a multi-floor house its [main view](#floors-and-the-whole-house) (the whole house by default, Phase 16.1), rendered read-only on the dome stage, navigated like the builder (Phase 14.6: orbit, pan, and zoom with the trackpad, mouse, or touch gestures of the chosen **Navigation**), within limits.

## Out of scope

- Production delivery is outside this dev milestone, but integration hosting, a built bundle and local copies are now specified in [production integration](production-integration.md). Add-on/ingress and broader publishing remain deferred.
- Devices, entity/action bindings, controllables, light state driven by HA, gestures, popups ([D15](../decisions.md#d15-card-interaction-and-state-policy)).
- Floor switching, editing, selection, picking, exports, photoreal mode.
- Hot module replacement. You reload Home Assistant by hand while developing.
- Editing dashboards or cards. The panel only displays the cards of an HA dashboard; they are authored in HA itself.

## Stack

The viewer is a **separate front end** with its own conventions. Builder rules (React, React Aria, Tailwind `.tw.css`, `SchemaForm`, `/ds` workbench) do not apply to it.

| Concern | Choice |
| --- | --- |
| UI | **Lit** custom elements with TypeScript |
| Styling | Lit `css` blocks using **Home Assistant theme variables** (`--primary-background-color`, `--primary-text-color`, `--card-background-color`, `--divider-color`, `--ha-card-border-radius`, and so on). One shared `tokens` stylesheet holds viewer-only values such as stage grays. No Tailwind. |
| Look | Native Home Assistant. Use HA elements (`ha-card`, `ha-icon`, `ha-state-icon`) only where they are already defined in the frontend; never assume a lazily loaded one exists. |
| 3D | Three.js in a framework-free `HouseViewer` class |
| House rendering | The builder's framework-free renderer modules in `src/renderer/` (floor scene, instance layer, template/material/texture caches) plus `shared/` for document types and geometry. Assets (template glTFs, images) load through the API. Nothing else from `src/` is imported; ESLint enforces this. |
| Data | `house.json` and template assets from the existing [API](../architecture/api.md) |

`shared/` and `src/renderer/` import only three.js and `shared/` (no React or stores), so the viewer draws the house exactly as the builder's 3D view does. The viewer owns the stage, lighting, camera, and render loop.

## Loading in Home Assistant

### `configuration.yaml`

```yaml
panel_custom:
  - name: homeplan-panel            # custom element tag defined by the module
    url_path: homeplan
    sidebar_title: Homeplan
    sidebar_icon: mdi:home-variant
    module_url: http://builder.local:5173/ha-viewer/main.ts
    embed_iframe: false
    trust_external_script: true
    require_admin: false
    config:
      mode: dev
      api_base: http://builder.local:5173/api
```

- HA creates `<homeplan-panel>` and sets `hass`, `narrow`, `route`, and `panel` on it. `panel.config` carries `mode` and `api_base`.
- Changing this block needs an HA restart. Changing code needs only a browser reload.
- `embed_iframe: false` keeps the panel inside HA's DOM, so HA theme variables reach it and HA elements can be used.
- HA draws no header for a custom panel. On narrow screens the panel renders its own menu button that fires `hass-toggle-menu`.
- `config` is readable by every HA user. Never put secrets in it.

### Dev server

- The module URL points straight at a TypeScript entry served by Vite. Vite compiles it on request; there is no build step and no bundle in dev.
- Because the entry imports no CSS, Vite's client (`/@vite/client`) is never loaded and no HMR socket opens.
- Vite needs these settings ([vite.config.ts](../../vite.config.ts)):
  - `server.host: true`, so HA's browser can reach the Mac on the LAN.
  - `server.cors.origin` set to the HA origin (for example `http://homeassistant.local:8123`), applying to both modules and the `/api` proxy.
  - `optimizeDeps.entries` including `ha-viewer/main.ts`, so `three` and `lit` are pre-bundled before the first panel load.
- HA must be opened over **http** while developing. An https HA page (for example through Nabu Casa) blocks the http module as mixed content.

## House source

```ts
type HouseSource = {
  listHouses(): Promise<HouseCard[]>;
  loadHouse(houseId: string): Promise<{ revision: number; document: HouseDocument }>;
  templateUrl(houseId: string, templateId: string, version: number): string; // t_… under the house, else builtin
  imageUrl(houseId: string, imageId: string): string;
  readSetup(): Promise<ViewerSetup>;
  saveSetup(setup: ViewerSetup): Promise<void>;
};
```

The dev implementation calls `panel.config.api_base` with the existing routes: `GET /api/houses`, `GET /api/houses/:houseId/document`, and the template and image file routes. It validates responses with the shared TypeBox contracts and shows an error state on failure. Houses with `status: "invalid"` are listed but cannot be chosen. The [production adapter](production-integration.md#viewer-data-adapter-and-private-assets) replaces transport/storage at this seam and adds revision-pinned authenticated asset loading. It must retain the actual interface's bindings/dashboard/Settings methods (inspect `houseSource.ts`; the abbreviated example above is historical). Nothing outside `houseSource.ts` knows URLs.

**Demo source** (the website's [live demo](../product/showcase-website.md#live-demo)): `panel.config = { mode: "demo", data_base }` selects `createDemoHouseSource`, which reads one house from static files under `data_base` (`preferences.json` as the preferences response, `houses/<id>/document.json`, `templates/<id>/v<n>.glb`, `images/<id>.png`; written by `npm run demo:data`). It is read-only: it has no house list, every save rejects, and it sets `readOnly`, so Edit mode needs an HA admin (as in the integration) and the room gear is hidden. The render counters are off.

## Setup

- **Storage:** the setup is installation-global ([D12](../decisions.md#d12-user-identity-and-access)) and lives in the builder's [preferences document](../architecture/application-preferences.md) as `homeAssistant.viewer = { houseId, testEntityId }`, both nullable; `testEntityId` is no longer used (always null since 2026-11-16) and stays only so older settings remain valid. `homeAssistant.viewer` is added to the `PATCH /api/preferences` allowlist; the owning API and preferences specs are updated with it.
- **Screen:** shown when `houseId` is unset, or from a settings button on the viewer.
  - A house list from `listHouses()`.
  - Save writes the preferences with `expectedRevision`. On a `409` conflict the screen reloads the current setup and asks again.
- These are the only form controls in the viewer, and they are plain Lit markup, not `SchemaForm`.

## Reactivity

Home Assistant assigns a new `hass` object to the panel on **every** state change of **any** entity. Rendering must not follow that.

- `set hass(h)` only writes `h` into a framework-free `hassStore` and returns. The panel element itself does not re-render on `hass`.
- `hassStore` keeps the previous `hass.states` and, on each update, notifies only subscribers whose entity's state object changed. HA keeps the same object for entities that did not change, so reference comparison is enough.
- `EntityController` is a Lit `ReactiveController` that subscribes to one entity ID and calls `host.requestUpdate()` only when that entity changes.
- `HouseViewer` subscribes to the store directly, without going through Lit. In this MVP it subscribes to nothing.
- Theme or language changes (`hass.themes`, `hass.locale`) are separate store keys with their own subscribers.

**Check:** with the debug counters visible in dev mode (bottom right), toggling an unrelated entity increments no render count.

## `HouseViewer`

A plain class, not a Lit element:

```ts
class HouseViewer {
  constructor(canvas: HTMLCanvasElement, options: { assets: HouseSource; onFloorSelect?; snapshot?; … });
  /** The whole house or one floor (16.1); `slide` animates a floor switch (16.3). */
  showView(document: HouseDocument, view: ViewerView, slide?: "up" | "down" | null): void;
  resize(width: number, height: number): void;
  dispose(): void;
}
```

- **Units:** the model is in mm ([D03](../decisions.md#d03-coordinates-units-and-floor-local-geometry)). Like the builder, a plan root maps plan (x, y, h) mm to Three.js (x/1000, h/1000, −y/1000) m. The house is centered at the origin with its floor on `y = 0`.
- **Content:** the builder's floor scene (RealFloor, RealAllWalls, carpets, authored materials and textures) and instance layer (doors, windows, objects, light fixtures from their glTF templates). Light objects render their fixtures only; lighting comes from the stage, not from authored lights.
- **Ambient effects:** the builder's effects layer ([D24](../decisions.md#d24-ambient-effects)) plays each object's swirls and vapour every 20 s, out of sync, with view-only frames that never redraw the shadow maps; they are hidden in the glass reflection. Since Phase 8.4 an effect with a [binding](bindings.md#effects-in-the-viewer) runs only while its **Runs when** condition holds, with the first holding variant's look; an inactive effect has no timer and requests no frames, and with every effect inactive the viewer renders only on other changes. An effect without a binding plays as authored.
- **Not rendered:** guides, helpers, pins, the ground grid, selection, or anything from the builder's editor layers. Saved **Hidden** things (Phase 7.5) are never drawn: `showHouse` passes the floor through `viewerFloor` (`ha-viewer/viewerFloor.ts`: the builder's `floorView` with `viewerVisibility`); a hidden room takes its walls and contents with it. Unlike the builder, a hidden light is left out entirely: no light, fixture, bubbles, or Settings row, because Hidden here means "there, but not in use right now" (owner, 2026-11-17). Settings lists the same floor, so hidden rooms, objects, and lights have no rows.
- **Stage:** a screen-fixed backdrop, not 3D. The canvas is transparent over a CSS background: a sky fading from white to a light-gray horizon, and a large half-ellipse floor rising from the bottom edge (its faint rim forms the horizon arc) with a lighter area where the house stands. HA dark mode switches it to dark grays. It never moves with the camera. The backdrop layer is oversized and shifts very slightly with camera tilt as a parallax cue (5% of its height per radian from the default view; tilting down toward the floor lowers it (owner preference)). The viewer sets a CSS variable directly, without a Lit render. **Follows the house** (Phase 14.5): while floor widgets or room cards take part of the screen, the glow and the floor ellipse (day and night) move 35 % of the way from the screen centre toward the centre of the free area the house is framed in (implementation convention, to tune with the owner), driven by the camera's sprung frame insets (`HouseViewer` `onInsets`, every frame of the spring), so they move in step with the house and return to the centre when nothing is shown. Only the gradients' centres move (CSS variables `--hp-orb-dx`, `--hp-orb-dy` in px); there is no extra render pass. There is no shadow catcher: shadows fall only on real surfaces (floors, carpets, walls), never into the air around the house (owner). In 3D there can be, 12 mm below the floors, a faint glass-like reflection of the house (a half-resolution mirror pass that is transparent where it reflects nothing and fades out with distance from the house). The reflection shows only walls and wall openings (doors, windows); objects and light fixtures are hidden during the reflection pass. **Off by default since Phase 21** (owner, 2026-11-20, to optimise rendering): it draws the house a second time every frame (measured on the demo Family house's ground floor, desktop: 11.5 ms a frame with it, about 4 ms without); it stays available as the viewer property `HouseViewer.setReflection(enabled)` for a later setting. Lighting: a faint room environment plus the builder's sun and sky, driven by Home Assistant's real sun (see [Sun, shadows, and night](#sun-shadows-and-night)). Shadow flags come from the builder's layers (walls and objects cast; floors and carpets only receive), which avoids shadow acne on floors. Walls cast from both faces (Phase 21, owner report 2026-11-20: at night a lit room's light spilled into a dark neighbouring room along the corners where walls meet; with back faces only, the joints of the merged walls let a sliver of a lamp's light through its shadow map; `floorScene.applyMaterials` sets the wall layers' `shadowSide`, so the builder gets the same fix).
- **Camera:** perspective, looking diagonally down at 52° elevation and 35° azimuth (owner 2026-11-16: about 30° was too frontal and too far out), at the closest distance where the floor's real outline fits the free part of the screen (Phase 14.3, owner: about 20 % closer than the earlier fit of the bounding box, which was symmetric about the box centre and wasted the margin on the far side). The outline is every floor shape's corners at floor level and every wall band's corners at floor level and at the band's own height (`ha-viewer/three/floorFraming.ts`, pure, checked by `npm run viewer:focus` on wide, square and narrow screens with widgets on each side). The fit is exact for the perspective view: the orbit target stays on the box centre wherever that fits and slides within the view plane only as far as the outline needs; the outline fills at most 1/1.04 of the free window (a 4 % margin); the view is shifted down slightly (5 % of the free height) so the house sits on the glow, and the fit allows for that shift. Against the box fit this is about 18 % closer on wide screens (where the height binds), a little closer on square and narrow ones (where the width already bound tightly; closer would cut the house), and more for houses that do not fill their box (an L-shaped house about 23 %). It is refitted when the floor widgets or the screen's shape change. Room framing is separate ([room cards](#room-cards)). The near/far planes follow the camera distance to keep depth precision high. Polar angle clamped between about 10° and 80° for gestures, so the camera never goes under the floor (Top view goes past the upper limit; from there gestures only tilt back down); zoom limited to between about 0.6× and 2.5× the framing distance (widened to include a room's framing); the camera returns to the default framing on a double tap on empty space.
- **Navigation** (Phase 14.6, owner 2026-11-18: navigate like the builder; the earlier OrbitControls drag-to-orbit could not pan): the builder's framework-free gesture map `src/renderer/navigationInput.ts` (D16) drives the viewer's own orbit camera (`ha-viewer/three/viewerOrbit.ts`, which implements the map's narrow `NavigationTarget`: pan at the target's depth, orbit about the target, zoom toward the point under the pointer, at the builder's rates), so the same gesture does the same thing in both hosts. The viewer has no tools, so its primary presses (which the builder forwards to its tools) are taps or camera drags (`ha-viewer/three/dragNavigation.ts`). **Settings → House → Navigation** chooses how the wheel reads:
  - **Trackpad:** two-finger scroll orbits, Shift + scroll pans, pinch (wheel + Ctrl, or Safari's gesture events) zooms at the pointer.
  - **Mouse:** the wheel zooms at the pointer; middle-drag orbits, Shift + middle-drag pans.
  - **Touch:** the wheel reads as a mouse wheel (a touch device's occasional wheel is a mouse's).
  - In every mode: a primary drag (mouse or pen) orbits and Shift + drag pans; with touch, one finger orbits, two fingers pan, and pinching zooms at the fingers' midpoint (touch input is recognised by its pointer type, so a touchscreen laptop in Trackpad mode keeps it). Pan works in the whole-floor view and in a room; the orbit target stays within the floor's half-diagonal + 1 m of its centre (and from 1 m below the floor to 4 m above its walls), so the house cannot be lost. Implementation conventions.
  - **Taps:** a drag starts only past the 6 px tap slop, so a tap never moves the camera, and a press that dragged, or that a second finger joined, never fires a tap, hold, or double tap. Picking is unchanged.
  - **Spring moves:** grabbing the view (a drag, a scroll, a pinch) stops a running spring move's pan, turn, and zoom; its frame insets spring on, so the house still settles into the space the cards or widgets leave.
  - **Setting:** `homeAssistant.dashboard.navigation` (`trackpad` | `mouse` | `touch`), installation-global (owner, 2026-11-18: fine for now; a per-device choice may come later) and optional: absent, it is **Touch** on a touch-first device (`(pointer: coarse)` and no `(any-pointer: fine)`) and **Trackpad** otherwise. Saved with Settings' Save like the other dashboard fields; the integration's `SnapshotDashboard` carries it optionally and the HA store copies it on the one-time global import (with `urlPath`).
- **View buttons** (Phase 14.6; the builder's camera buttons without the orientation gizmo, owner): a small vertical group of round buttons (the top bar's style, the builder's icons) at the bottom-left of the free area the house is framed in (the bottom-right while floor widgets take the left side, the top-left while they take the bottom; owner, 2026-11-18), so they keep clear of the floor widgets and the room cards and glide with the frame insets; shown once the house is loaded, also in Edit mode and with the room gear open. From the top: **Look straight down** (azimuth 0, so plan X is right and Y up, as the builder's Top (3D)), **Rotate the view 90°** (a quarter turn about the vertical), and **Fit to screen**. Each is a spring move and ends fitted: on the whole floor the outline fit (14.3) at the new angles (Fit returns to the default 52°/35° framing); in a room, the room's framing (its saved position or its fit) at the new angles (Fit returns to the room's own angles). A resize or a widget change refits the floor at the current angles. Further presets come to the viewer as the builder adds them.
- **Lifecycle:** render on demand, through the viewport's one frame scheduler (Phase 15.3, [renderer lifecycle](../architecture/renderer.md#lifecycle-and-performance-rules)): a change requests one frame, and frames continue only while an animation is active: the camera spring move (`camera` channel), object-state animations (`states`), or staged asset work (`assets`). They are independent: orbiting, panning, or zooming during a door, blind, or AC animation stops only the camera move's camera part (its frame insets spring on) and never the other animations, which reach their latest target; ambient effects keep ticking through continuous frames. Once nothing is active the frames stop; a later HA change or gesture wakes them. A `ResizeObserver` drives `resize`. When the panel element disconnects, `dispose` cancels every animation and frees the renderer, geometries, materials, and textures.

Stage and camera values are implementation conventions; tune and record them in code.

## Loading and the opening sequence

Phase 15.1 (owner: the opening stuttered while everything loaded at once; objects were black until their textures arrived). Before, the house model was built at once, every template and image was requested on the first sync with no limit, every finished template re-synced all instances and redrew all shadow maps, and textured materials sampled empty textures (black). Now `HouseViewer` stages it (`ha-viewer/three/houseViewer.ts`, `src/renderer/loadQueue.ts`):

1. **Preparing:** the house model (floors, walls, carpets, and its doors and windows, whose templates load first so the sky-light window portals are known before any shader compiles) is built with plain colours: house textures are not loaded yet, and a material never samples a missing texture (it draws its base colour, tinted by the image's remembered average colour, `ha-viewer/swatchMemory.ts`). Its shaders, with the sun, lamps, and shadows, compile in the background (`renderer.compileAsync`); nothing is drawn meanwhile, so the backdrop shows. The first frame draws the shadow maps while the canvas is still transparent, then the canvas fades in (0.35 s). A camera move that arrives meanwhile (the floor widgets' framing) lands at once, so the house appears already framed beside the widgets.
2. **Opening:** the camera move and the floor widgets' layout run alone, with static shadow maps. The opening has settled when no camera move has run for 400 ms (ambient effects and state animations do not count), or at the latest 5 s after the house appeared.
3. **Loading:** house textures, then the separate objects (furniture, fixtures), load through the queue, 3 at a time. Images decode off the main thread and upload to the GPU a few per frame (at least one, more within 4 ms); a material takes its map once the mapped shader has compiled in the background. Finished templates are added in batches, at most every 120 ms, with one instance sync per batch; each batch waits on a layer no camera renders until its shaders have compiled, then shows. Until its batch, a loaded template counts as loading for the instance layer (a placed view of the template cache), so no other sync (an HA state, a light) places it early. Shadow maps are redrawn at most every 500 ms for these additions (HA state and light changes still redraw them at once). A thin bar under the house (`.load-bar` in the free area, HA accent on the divider colour) shows the share done and fades out at the end.
4. **Done:** one final shadow pass; templates that load later (another floor) are placed at once.

Stage values are implementation conventions (`houseViewer.ts` constants), to tune from measurements. **Measuring:** in dev mode (the harness), or with `localStorage["homeplan.loadTiming"] = "1"` (or `?homeplanTiming` in the URL) inside HA, the viewer logs per-stage timings to the console (`ha-viewer/three/loadTiming.ts`: template fetch and parse, flatten, image fetch and decode, uploads, background compiles, object batches, the first and later shadow-pass frames, and each stage's frame count, worst render time, and frame gaps over 34 ms); there is no timer, loop, or UI in production.

## Floors and the whole house

Phase 16.1 and 16.3, owner decisions 2026-11-18; `ha-viewer/floorNavigation.ts` (pure, `npm run ha:conditions`), `ha-viewer/three/houseViewer.ts`, `src/renderer/houseExterior.ts`. A house with more than one floor has three view levels: the **whole house**, a **floor**, and a **room** of that floor. A one-floor house is unchanged: it opens on its floor, with no floor controls and no Main view setting.

- **Main view:** a multi-floor house opens in the whole-house view, unless **Settings → House → Main view** (shown only for multi-floor houses) names a floor: **Whole house** (the default) or a floor by name, keyed by its floor ID (a rename keeps the choice). Installation-global HA configuration per house, a Settings draft saved with Save. A configured floor that was deleted, or is missing from an upgraded snapshot, falls back to the whole house; a house that became single-floor opens on its floor and hides the setting. Ordinary navigation never changes the saved choice. **Storage:** `homeAssistant.dashboard.mainViews[houseId] = floorId` (optional; absent: the whole house; the empty map is left out on Save, so a Save from a viewer whose integration predates 16.1 does not send it). Schema: `HaDashboard` (`shared/domain/schemas/homeAssistant.ts`); the integration's `SnapshotDashboard` carries it optionally and the HA store copies this house's entry on the one-time import, like the room tabs.
- **Whole-house view** (16.1; complete since Phase 18.1, owner 2026-11-18: "display all elements", replacing decision 7 of 16.1, walls, windows and slabs only): every floor **complete**, stacked at its [placement](../builder/model.md#floor-placement-and-slab) (plan offset and finished-floor elevation), built by the framework-free `src/renderer/houseExterior.ts`: per floor the builder's floor scene (RealAllWalls with their openings cut, room floors, carpets, textures, slab with its stair cuts) and one instance layer with everything the floor view draws: furniture, stairs and floor openings, the **real door and window templates**, wall-mounted items, trees, light fixtures, and the yards' fences and gates. Every floor's **lamps** shine with their current HA state (one lights layer for the whole house, [complete floors](#complete-floors-in-the-whole-house)). Open at the top (no visible ceiling); a floor's **roof** (Phase 19.1, [roofs](../builder/features/roofs.md)) is drawn here, casting shadows, and only here: opening a floor shows it without its roof (owner decision 4, 2026-11-18: HA is for controlling the home, and rooms under a roof could not be seen). A click on the roof opens its floor. A one-floor house has no whole-house view in HA, so its roof is not shown there (19.1 limit). Its walls are still clipped by it and rise to it in every view, the floor view included (Phase 19.2, [the roof cuts walls](../builder/features/roofs.md#the-roof-cuts-walls)): that is wall geometry, not the roof. Phase 19.3: the roof's holes, roof windows (their templates load like the doors and windows) and step faces are drawn with it, and the shadow-only ceilings under it no longer shade its top (the attic's dark band). A floor's **attached canopies** (Cuts walls off, e.g. over a terrace) are drawn in its floor view too, unlike the roof (a proposal for the owner to confirm, [canopies](../builder/features/roofs.md#attached-canopies)); a tap passes through them. 19.3 adds only optional fields (no schema version change) but needs a reinstall for `schemas.json`, the viewer and the two roof-window templates. A stored copy of house schema version 4 or 5 (roof cuts) is migrated on load ([migration](../builder/features/roofs.md#migration-of-roof-cuts)); the integration validates all three versions, so 19.2 needs a reinstall for `schemas.json`. Not drawn there: ambient effects, TV screen pictures, bubbles, floor widgets, presence sweeps, room interactions. The house is framed like a floor (the outline fit of every wall band and slab corner, 14.3, plus the ends of the yard fences), at the default angles; the view buttons work on it. A host without templates (checks) draws the doors and windows simplified as in 16.1 (a frame around a glass pane, or a plain leaf).
- **Selecting a floor:** one tap or click on a floor opens it (with the transition); taps there never reach rooms or objects, also in Edit mode (Settings then lists no things: "open a floor to connect its things"). With a mouse, hovering shows the floor's **bounding box** (owner, 16.13) in the accent colour: the axis-aligned box of its walls and slab coverage, from the slab underside to its wall tops, drawn over everything as screen-space lines 3 px wide (`highlightLinePx`, implementation convention, thick enough to read on a tablet; Three.js `LineSegments2`, not tone-mapped; each floor's box is built hidden with the floor so its shader compiles with the house), and the cursor becomes a pointer; touch has no hover. Two taps on empty space reframe.
- **Floor controls:** beside the view buttons (above Top view, Rotate and Fit, same style), multi-floor houses only: **Whole house** (a house icon; disabled in the whole-house view), **Up a floor** and **Down a floor**. The order is by finished-floor elevation (`floorsByElevation`; ties keep document order); the whole house counts as above the top floor, so **Up from the top floor goes to the whole house**, Up is disabled in the whole-house view, Down there goes to the top floor, and **Down is disabled at the bottom floor**. On a switch the destination's name (or "Whole house") shows for 1.6 s under the top bar (implementation convention). **With a room open** (decided, the recommended rule): the controls stay available and act on floors, so a switch first closes the room (its cards, settings, and corner picking), then switches.

### Floor switch transition

Phase 16.3, revised by the owner's 16.13 feedback (2026-11-18), rebuilt in Phase 21.5 (owner 2026-11-20: keep every floor's shell loaded, swap at once, add the destination's objects after the ride with the loading bar). The first version (the departing view as an image sliding and scaling) read as a parallax scale in and out; the second (16.13) kept a copy of the departing view with its own lights and a full-screen render target and blended it over the destination, which cost about 75 MB on a phone and two renders per frame, so the ride stuttered. The owner's intent, in their words: like being "in an elevator outside of the house" moving up or down, the house "stacked as it normally is", nothing moving forward or backward; then a separate fit of the destination. Implementation: `HouseViewer.showView(…, slide)` with `ha-viewer/three/floorTransition.ts` over the house's one set of floors (`src/renderer/houseExterior.ts`, [one set of floors](#complete-floors-in-the-whole-house)); conventions are constants there.

1. **Departing frame held:** the canvas keeps showing the departing view's last frame while the destination prepares (nothing is drawn meanwhile; the `data-preparing` fade-out is held off). The departing camera and the departing view's place are kept; nothing is copied.
2. **Destination prepared first** (the [staged opening](#loading-and-the-opening-sequence), 15.1): every floor's shell is already built, so a switch builds no geometry. The destination is shown at its place (a floor at the plan root's origin, `setFocus`), the **floors above it hidden at once** and the floors below it shown for the ride; the departing floor's objects are removed at once (only the shown floor keeps its content, `setContentFloors`). The viewer's layers (lights, effects, sweeps, overlays) follow the destination at once; its house model (walls, floors, slab, doors and windows) compiles in the background with its final lights (16.6). The destination's objects are held back: only its doors and windows are placed now (objects it already draws, entering a floor from the whole house, stay). The first frame draws the shadow maps.
3. **The ride:** about 0.6 s (600 ms, ease in and out), one animation on the frame scheduler's `floor` channel (15.3). The camera starts where it was, moved with the departing view's content to its real place relative to the destination (the difference of the two views' origins: each floor's `floorToHouseOffset`, the house's zero for the whole house), and ends exactly above or below it by the floors' elevation difference: **same azimuth, polar angle, distance, and horizontal position**, so the ride is a pure vertical translation (`slidePose`; no zoom, no re-fit; the pan limits widen as needed). It draws the house's real floors, one render per frame: the destination and the floors below it, stacked as they are. Whole house ↔ floor rides the same way. **Only the camera moves**, so no shadow map is redrawn during the ride.
4. **Objects after the ride:** when the ride ends, the floors below are hidden again (the shadow maps redraw once) and the destination's objects load with the loading bar, at most 6 templates per batch (`admitBatchTemplates`), each batch compiled in the background before it shows, so they arrive in steps, not at once.
5. **The fit:** when the ride completes, a separate move on the `camera` channel (the usual camera spring) fits the destination at the kept angles. A ride ended by a new switch starts that switch's ride from where the camera is; a resize ends the ride and reframes; a new switch during the fit stops the fit where it is and rides from there.
6. **Lights:** the destination's own lights light the ride; the departing floor below is lit by them too (its lamps are not drawn during the ride).

**Measured** (harness, demo Family house, desktop Chrome, pixel ratio 2, 2026-11-20; 16.13's copy in brackets): floor → floor up, first visit on a fresh page: house-model compile 48 ms, first frame 125 ms, ride frames 7.9 ms on average, then 6 object batches about 120 ms apart; switching back down to a visited floor: worst frame 68 ms, 197 ms of long tasks in total [23 frames over 33 ms]; whole house → floor again: worst 55 ms [a 1.4 s freeze]; geometries in a floor view 1,510–1,688 [5,629: the floor was built twice]. The very first time a browser meets a light topology its compile can take seconds (seen once at 2.5 s on desktop); later visits reuse it.
- **Whole house ↔ floor:** the same transition (a vertical ride, then the fit); the whole house is "above" every floor in the floor order. Entering a floor keeps that floor's objects and drops the others'; going back to the whole house loads the other floors' objects again (from the cached templates, with the bar), and the house merges again once settled.
- **Live bindings** (16.3, 18.1): the live evaluator follows only what the shown view draws live. A floor (`floorBindings`): its lights, objects and openings, their effects, its rooms with their presence and room bubbles, placed bubbles on its things, its own presence gate. The whole house (`houseBindings`, 18.1): the lights and the objects, doors and windows of **every** floor (lamp states and live state parameters), nothing else (no effects, rooms, bubbles, presence or gates; it takes no object taps, so actions need no listener). A switch unsubscribes the departing view's entity listeners (HA's global state delivery is untouched) and the destination starts from HA's current state. Settings keeps every floor's bindings.
- **Interruptions:** a switch during preparation keeps the departing frame and the ride's start and prepares the new destination instead (the earlier preparation's callbacks are dropped by the stage token); a switch during the ride snaps it to its end, then rides afresh from there; a switch during the fit stops it where it is; a resize ends a switch at once and reframes; off screen (16.11) a switch shows no ride, and a ride in progress waits and ends on the first frame back; disposal cancels it. However it ends, the ride settles exactly once into the end state (the floors below hidden, the camera at rest, the canvas's own styles). A view that fails to build leaves the previous view shown (rebuilt without a slide) and says "Could not open …". `npm run frames:check` checks the lifecycle on a fake clock, the camera path (`slidePose`: a pure vertical translation), and the ride's progress from exactly 0 to exactly 1; `npm run ha:conditions` the order, the main view and its fallback, and the live bindings; `npm run slabs:check` the exterior.

### Renderers (per device)

Phase 21.11 (owner design, 2026-11-20). A renderer takes the shown house and draws the screen: the frame draw, the room fade (dither or transparent copies) and its levels, the sharpness and shadow limits, the glass reflection, the backdrop (the glow and floor, or plain sky), and whether a floor switch's ride shows the floors below. The viewer lists the renderers; **each device picks one**, stored in that browser (`localStorage` `homeplan.renderer` and `homeplan.renderer.<id>` for its settings), read once when the viewer starts, so a change reloads the page. Not per HA user: D12 stays (owner agreed). Code: `ha-viewer/three/renderers.ts`, a base class `ViewerRenderer` whose methods the viewer calls at each step; a renderer extends it (or another renderer) and overrides only what differs. New renderers are added to `rendererList` as reviewed code (pull requests); nothing is loaded at runtime.

| Renderer | Room fade | Limits | Settings |
| --- | --- | --- | --- |
| **Dithered** (default) | dither | sharpness 2, the GPU's lamp-shadow budget, 512 px lamp shadows | **Other rooms visible** 3–50 % (default 10 %); the walls in front of the room keep 2.5× as much, at most 75 % |
| **See-through** | transparent copies (the earlier look; each room open rebuilds walls and compiles) | as Dithered | none |
| **Low power** | dither | sharpness 1.5, 4 lamp shadows at 256 px; the ride shows only the destination | as Dithered |

Every built-in renderer draws the glow backdrop and no reflection. **Writing a renderer** (a contribution): add a class to `ha-viewer/three/renderers.ts` that extends `ViewerRenderer` or a built-in renderer, give it an `id`, `label` and `description`, override the steps it changes (`draw` for the frame itself, `roomFade`, `ditherLevels`, `limits`, `reflection`, `backdrop`, `floorsBelowDuringRide`), declare its adjustable values in `settingsSchema` (sliders on Panels, read with `setting`), and add it to `rendererList`; run lint, typecheck and `npm run frames:check`, try it with the fake viewer's Renderer button, and open a pull request. The picker is on Settings → Panels, **This device** (admins, since Settings is for admins); the fake viewer has a button that cycles through them.

### Complete floors in the whole house

Phase 18.1 (owner 2026-11-18). Decisions and implementation conventions, measured on the demo Family house (3 floors with an attic, 129 objects, 41 doors and windows, 38 lamps, two yards; harness, desktop Chrome, 2026-11-18):

- **Staged loading** (15.1 unchanged): the house model is every floor's walls, floors, slabs, doors, windows and yard fences (their templates on the house lane, at most 2.5 s), compiled in the background with every lamp (off at zero output) before it fades in; the opening move runs alone; then each floor's objects and textures load through the same queue (three in flight), batch by batch with background compiles, the **likely floor first** (`setLoadOrder`: the floor shown before the whole house, else the floor nearest the ground, then document order). Hover does not reorder loads already queued (limit).
- **One light topology, a smaller shadow budget** (16.6): one lights layer lights every floor's lamps (areas in their own floor's group), so the topology stays fixed per view and no switch compiles. The whole house has its own shadow budget, `houseShadowBudget` = 4 (`src/renderer/lightsLayer.ts`): the brightest lamps that are on cast first (the 16.6 slot rule), the rest shine unshadowed; a floor view goes back to the floor budget (9 on most GPUs). Measured: 4 casters, 0 programs compiled on the first and later switches (one lamp, two, all 38 on, all off), 15–30 ms to the next frame. Limit: an unshadowed lamp is not confined by walls or slabs, so a bright upper lamp can faintly light the floor below it.
- **Static batching** (`src/renderer/staticBatch.ts`): once loading is done and nothing has changed for 300 ms, each floor is merged, one floor per 50 ms step (17–45 ms each): its drawn opaque meshes become one mesh per material, attribute layout and shadow flags, in two buckets (objects, which stay out of the glass reflection like the objects themselves, and the house); light fixtures, transparent and multi-material meshes stay as they are. The sources move to a layer no camera renders, and a change that no longer matches a floor's batch (a live state rebuilding an instance, a material change) drops that floor's batch at once until it merges again. Measured: 3998 meshes in 370 draws; a frame 2693 → 353 draw calls, 30.5 → 8.6 ms render (idle; 29.3 → 7.7 ms orbiting), against 8.7 ms for the ground floor's own view (1097 draw calls); no shader compiled by merging. Before merging (while loading) a frame costs the unmerged 30 ms.
- **One set of floors** (Phase 21.4, owner 2026-11-20, replacing 18.1's reuse): every floor's shell (walls, floors, carpets, slab, roofs) is built once, when the house is shown, and kept for as long as the house is; a floor view draws its floor from that same set (`floorParts`: its floor scene and instance layer, so the cutaway, sweeps, sky light and picking work on it), with every other floor hidden, its roofs hidden (a floor view draws only attached roofs) and its batch dropped (a floor view picks per area). Only the shown floor keeps its objects: entering a floor removes the other floors' objects, and the whole house loads them again. Measured: a floor view holds 1,510–1,688 geometries instead of 5,629 (18.1 kept the hidden whole house beside a second copy of the shown floor); going back to the whole house rebuilds the other floors' objects from cached templates (worst frame 167 ms, about 55 ms frames until merged again).
- **Opening** (cold, first visit): shells at about 0.2–0.5 s (doors and windows fetched), complete at 1.7–3.9 s (80 templates), merged 0.5 s later; frames during the opening 2 (the first with the shadow passes 160–210 ms warm, 1.5 s on the very first load with its shader compiles), loading frames 25 ms average (unmerged), no gap over 34 ms in the loading stage.
- **Listeners:** the whole house follows the lights and things of all floors (the owner wants every element shown live). The evaluator subscribes once per distinct entity, in the viewer's own store over HA's one `hass` delivery (no extra HA subscription), so the cost is the number of entities bound to the house's lamps and things, for the demo house up to 38 lamp entities against up to 16 on its ground floor.
- **Checks:** `npm run slabs:check` (the exterior kept across syncs, load order, area groups, merging and a changed floor dropping its batch), `npm run frames:check` (static batching: buckets, layers, frame, mirrored winding, staleness), `npm run lights:topology` (three floors in one layer: one light count, exactly the house budget casting, the brightest on lamps first, back to the floor budget), `npm run ha:conditions` (`houseBindings`).

## Bindings and Edit mode

Owner requirement (2026-11-16, light mapping in Phase 7; generalised in Phase 8.0 to every bindable thing, [D25](../decisions.md#d25-home-assistant-bindings)). Lights, objects (with their ambient effects and, from Phase 9.7, their state parameters; doors and windows too), and rooms are connected to Home Assistant in the viewer's **Edit mode**; the model, conditions, storage, and editor are specified in [bindings](bindings.md).

- **Edit mode:** the pencil icon button in the top bar toggles it. While on, a tap picks the bubble, else the light, else the object, else the room under it: a bubble opens its [bubble popup](#bubbles); anything else opens **Settings** with that thing selected (Phase 10.9); nothing runs and holds and double taps do nothing. In Edit mode two buttons appear in the top bar, just left of the pencil (owner, 2026-11-17): **Settings** (formerly "List") and **Done**, the primary (filled accent) button; the pencil also leaves Edit mode. The pencil and these buttons sit on a surface with a shadow so they stay visible over the night sky. There is no **Add Bubble** button any more (owner, 2026-11-17: removed; the placing function stays in the code); room bubbles are added under their room in Settings. Under the bar a small tip says what a tap does and where Settings and room bubbles are; its **×** asks whether to hide it for good (stored in this browser) or just now; a tip closed just now comes back the next time Edit mode opens.
- **Settings** (Phase 10.9, owner 2026-11-17; `ha-viewer/bindingEditor.ts`): one place for everything bound or configured. A dialog of 90 % × 90 % of the viewport, split: the left third is the tree (search with **Expand all** / **Collapse all** on top, Phase 10.8, shown as HA's `mdi:unfold-more-horizontal` / `mdi:unfold-less-horizontal` icon buttons with those names as tooltip and accessible name, Phase 16.12; always the tree, owner 2026-11-18; it scrolls on its own), the right two thirds the editor of the selected node (it scrolls on its own), and one **Cancel** / **Save** footer for the whole dialog. Opened from the bar it selects the **House** node with the tree fully collapsed; opened by a tap in Edit mode it selects that thing, opens its room (and group) in the tree, and scrolls its row into view. When the dialog would be at most 700 px wide (phones), it shows one pane: the list, then the editor with **Back**. The tree, the House node, the editors, and saving: [bindings: editor](bindings.md#editor).
  - **House node** (top of the tree), in this order (owner, 2026-11-18): **Room cards** (which HA dashboard the [room cards](#room-cards) come from), **Main view** (multi-floor houses only, [floors and the whole house](#floors-and-the-whole-house), Phase 16.1), **Navigation**, and last, in the HA integration, **House setup** (Floor Builder URL, Connect, the house list with **Use this house** / **Upgrade**, DEV MODE, Panel; [production integration](production-integration.md#floor-builder-connection-and-house-selection)). Before any house exists, **Setup your home** opens the same Settings with only the House node. The cutaway setting and **Swap house** were removed (owner, 2026-11-17).
  - **Room editor:** the room's binding (entity and actions, Shown when, Suggest for this room), its **Tab** (which dashboard tab shows the room), its [room bubbles](#bubbles), and its [presence and intrusion](#presence-and-intrusion).
  - **Light, object, door, or window editor:** the entity whose state the thing shows (for lights, the `light.*` entity) and the click, long click, and double click actions: HA's own dashboard actions (`toggle`, `more-info`, `perform-action`, `navigate`, `url`, `assist`, `none`), as HA's action editor produces them; **Shown when**, a condition (a subset of HA's card conditions); for objects their state parameters (9.7) and their ambient effects' conditions and variants.
  - **Saving:** everything in Settings is a draft until **Save** (bindings with room bubbles and presence, the dashboard, each room's tab, width and title); **Cancel** discards it. Save writes every changed preferences key in one revision-aware `PATCH` and applies it at once.
- **HA's own form elements:** `ha-form` with the `entity` (filtered to lights for a light), `ui_action`, `attribute`, `state`, `select`, `number`, and `color_rgb` selectors. HA loads these lazily; the viewer triggers loading through the public `window.loadCardHelpers()` (building the button card's config editor once). Outside HA, for example in the harness, plain controls are the fallback. HA fires `value-changed` as a plain `Event` with a `detail` property, not a `CustomEvent`.
- Condition badges show whether a condition holds now and re-render only when an entity it reads changes.

**Storage:** bindings are HA configuration, not builder data: `homeAssistant.bindings[houseId] = { lights, objects, effects, areas }` in preferences, each keyed by the builder's stable IDs so moves and renames keep them; a light binding is `{ stateEntityId?, tapAction?, holdAction?, doubleTapAction?, visibleWhen? }` (today's light mappings stay valid; documents from before 8.0 are migrated on read). `PATCH /api/preferences` with `homeAssistant.bindings` merges by house and kind. `house.json` never contains HA data. Schemas: [`shared/domain/schemas/homeAssistant.ts`](../../shared/domain/schemas/homeAssistant.ts); details: [bindings: storage and migration](bindings.md#storage-and-migration).

**Gestures** (outside Edit mode): a tap, hold (500 ms), or double tap (two taps within 280 ms) on a mapped light's fixture, an object with actions, a door or window with actions (10.1), or a bubble runs its action; drags beyond 6 px move the camera instead ([navigation](#houseviewer), `ha-viewer/gestures.ts`, one timing for all three). A tap waits for a possible second tap only when the target has a double-tap action. Unconfigured gestures default per kind: a **light** like HA's cards (tap toggles, hold opens more-info, double tap does nothing); an **object** with an entity (Phase 21, owner: every thing with an entity behaves like HA by default; before, only an AC reacted): HA's own default for its entity, as its button and tile cards (`haDefaultAction`, `ha-viewer/haActions.ts`): a tap toggles a domain HA's frontend toggles (`light`, `switch`, `fan`, `input_boolean`, `group`, `automation`, `humidifier`, `valve`) and opens more-info for any other (an AC's `climate` entity: more-info, as before), a hold opens more-info, a double tap does nothing; Settings shows each unset gesture as HA's **Default action (…)** (`ui_action` with `default_action`); a **door or window** (10.1, [opening gestures](bindings.md#opening-gestures)) with an entity driving its main state (its first state mapping's entity, the blinds mapping last, else `stateEntityId`): tap and hold open that entity's more-info, except that a tap toggles the tilt (`cover.toggle_tilt`) when its `blindsClosed` parameter is driven by a `cover` (a venetian blind, whose mapping is a band on the tilt, is set between shut and 50 with `cover.set_cover_tilt_position`, 10.4); double tap does nothing; a **bubble** (8.5): tap opens its entity's more-info (for a camera, HA's live view), a light-toggle bubble's tap toggles, hold and double tap do nothing. A tap draws no outline around the thing tapped (Phase 21.2, owner: the viewer does not need it). Two taps on empty space reframe the camera. Unmapped lights do not react; an object, door, or window without actions (unbound, no configured action, no default, or its Shown when failing) does not take the tap, which goes on to its room. Actions run in the viewer (the panel is not a Lovelace dashboard): `toggle` and `perform-action` call `hass.callService`, `more-info` fires HA's `hass-more-info` event, `navigate` and `url` change location; `assist` is not supported yet.

**Light states in 3D:** the viewer draws lights with the builder's lights layer. Each mapped light's authored defaults are replaced by its entity's state: on/off, brightness (`brightness`/255), and colour (`rgb_color`, or `color_temp_kelvin` in colour-temperature mode). The [binding evaluator](bindings.md#evaluation) subscribes once per entity any binding uses, so a change rebuilds only the lights that depend on it. A light whose **Shown when** condition does not hold is drawn off and ignores gestures. Unmapped lights are drawn off, because a live view should not invent light. A mapped light whose entity is missing, unknown, or unavailable is drawn off too (Phase 7.9, owner 2026-11-16: an unavailable Home Assistant must not show lights on). Lights cast shadows as in the builder, so walls confine them ([light confinement](../builder/features/lighting.md#light-confinement), Phase 7.10). Shadow maps are static: they are redrawn once when the house, a light state, or the framing changes, never while the camera moves, so a light change costs one heavier frame and orbiting none.

**Doors, windows, and blinds (Phase 9.7):** an object, door, or window whose binding maps entities onto its template's state parameters (an open angle, a window's open mode, blinds closed) is drawn with the live values instead of the stored ones, re-resolving only that instance through the builder's instance layer; house.json is not written, and an unavailable entity keeps the stored value. A change eases to the new pose over 600 ms (Phase 10.2; a jump with reduced motion): frames and shadow redraws run only while an animation is in progress, then stop, so the idle counter keeps counting afterwards. Details in [bindings: state parameters](bindings.md#state-parameters).

**TV screens (Phase 8.8):** an object whose template declares a [screen](../builder/features/object-templates.md#screens) and whose binding's entity is a `media_player` shows the running app (its `entity_picture`, else the app name as text) on the screen while the player is on, and the authored dark screen when it is off; details in [bindings: TV screens](bindings.md#tv-screens). A change renders one frame and redraws no shadow maps.

## Bubbles

Owner requirement K4, K5, K14, decision Q4 (2026-11-16), Phase 8.5. Two kinds of bubbles, one design; model and storage in [bindings: bubbles](bindings.md#bubbles).

- **Design:** an HTML overlay over the canvas (`ha-viewer/bubbleOverlay.ts`, Lit), never a 3D object: it always faces the viewer, keeps its screen size (34 px high), and uses HA's theme (`--card-background-color`, `--primary-text-color`, `--state-icon-color`, the active colour `--state-active-color` while the entity is on) and HA's own `ha-icon` (outside HA, a lettered circle). Content: the icon (the bubble's own, else the entity's `icon` attribute, else the preset's) and, by `format`, the value with its `unit_of_measurement` (`value`, one decimal at most), the state in words (`state`), or nothing (`icon`). Style `bubble` is a pill on the card colour; `bare` is the icon (and text) with only a drop shadow, e.g. a camera icon.
- **Positions:** after every 3D frame (camera moves and springs included; `HouseViewer` `onFrame`), the overlay projects each anchor and writes the transforms directly, so camera moves cost no Lit render and no extra 3D frame; Lit renders only when a bubble's content or set changes. Sizes are measured after Lit renders, never during a frame. Anchors behind the camera are not drawn.
- **Room bubbles (dynamic):** configured in Settings, in the room's editor → **Room bubbles** (Phase 10.9; saved with Settings' Save) (`ha-viewer/roomBubbles.ts`): Add bubble with a kind (temperature, humidity, light toggle, presence, state, custom), then its popup; rows show kind, entity, attribute, "conditional"; ↑ moves one earlier in the row. Those whose condition holds are drawn above the room: centred on its largest floor polygon's centroid, 250 mm above its highest wall top, in one row along the projection of the polygon's longest edge (read left to right, 8 px apart; `ha-viewer/bubbleLayout.ts`). They appear and disappear live as states change (the [binding evaluator](bindings.md#evaluation) subscribes once per entity).
- **Placed bubbles (static):** no button creates them since the owner removed **Add Bubble** (2026-11-17); existing placed bubbles still show, open their popup, and can be dragged in Edit mode. The placing function, kept for later, works as follows: a tap onto a light whose emitter is within 24 px on screen (hidden lights too) or whose fixture is under it, else the object (150 mm above its box top), else a free point in the room tapped (150 mm above the surface, or mid-height of the room volume when the tap hits only the volume). The new bubble's popup opens (Cancel discards it). Dragging a placed bubble in Edit mode re-places it where it is dropped (onto a light, an object, or a point). Always drawn, unless their condition fails.
- **Popup** (`ha-viewer/bubbleEditor.ts`): Entity and actions (the binding fields: `entity` and three `ui_action` selectors), Look (Kind, Shows, Attribute with HA's `attribute` selector, Icon with HA's `icon` selector, Style), Shown when (the condition editor), Delete / Cancel / Save. Plain controls in the harness. Save writes at once (`PATCH` of the house's `bubbles`).
- **Picking:** bubbles are picked first: their pointer events are handled on the bubble elements and stopped there, so the canvas (orbit and 3D picking) never sees them. The full order is bubble → light → object → room ([room cards: picking](#room-cards)).
- **Edit mode:** every bubble is drawn, those whose condition fails at 45 % opacity, each with a dashed outline; a tap opens its popup (a room bubble's popup edits it in its room's list and saves at once; the list itself is edited in Settings).
- **Hidden things** (Phase 7.5): a hidden room hides its room bubbles and the placed bubbles at points in it; a hidden object hides the bubbles on it. A hidden light is not in the viewer at all, so it has no bubbles either (owner, 2026-11-17).

## Sun, shadows, and night

Owner request (2026-11-16): the viewer shows the real sun at the real house.

- **Sun:** Home Assistant's `sun.sun` entity gives the live azimuth (clockwise from north) and elevation for HA's own location and time. Without it, the position is computed now from HA's configured `latitude`/`longitude` (`hass.config`); without that, the house's own environment (location and time) is used, as in the builder. The house's **North** turns the compass direction onto the plan (`sunDirectionPlan`, `shared/domain/environment/sun.ts`). Nothing is written to the house; its saved location stays as authored. The sun is re-read whenever `sun.sun` changes and every minute.
- **Lighting:** the viewer uses the builder's sun and sky (`createLighting`, `src/renderer/lighting.ts`) with the same rule (`sunSettingsFromPosition`): full sun from 6° elevation, fading to off at the horizon; the sky fill and the image-based fill follow daylight, and the exposure policy makes lamps carry the scene at night. Indoors (rooms under their shadow-only ceilings) both fills fall to the bounce floor by day and windows light their rooms as sky portals, as in the builder (`src/renderer/skyShading.ts`, [sky light through windows](../builder/features/lighting.md#sky-light-through-windows-phase-155)). Shadows follow the sun; a sun change redraws the shadow maps once.
- **Night backdrop:** while `sun.sun` is `below_horizon` (or the computed elevation is below 0°), a night backdrop fades in over 2 s: deep space: near-black at the top to a very dark blue-grey at the horizon, no stars (Phase 8.10), fixed on screen (no parallax), a dim moonlit grey-blue floor disc that alone follows the tilt parallax (toned down twice from whitish, owner 2026-11-16), then the house. Day keeps the light (or dark-theme) backdrop.

## Room cards

Owner requirement (2026-11-16, experiment; reworked in Phase 14.4, owner 2026-11-18). Tapping a room (its floor, contents, walls, or the space above it; not a light) zooms the camera to it and shows that room's Home Assistant cards on the right (a bottom sheet from 40 % of the height down under 700 px), 1 or 2 section columns wide (the room's **Columns** in Settings, default 1). The house is framed into the space the cards leave from the moment the room opens (`focusArea` gets the cards' insets; 14.1 fix): beside them on a wide screen (their width plus the 12 px screen margin and an 8 px gap, at most 70 %), above the sheet on a narrow one; the room fit uses both the free width and the free height. A change of the room's width or of the screen frames it again. Closing the room (the close button, or two taps on empty space) returns to the whole floor.

- **No panel** (14.4): like the [floor widgets](#floor-widgets), the cards are drawn over the 3D view with no panel surface; each card keeps HA's own card surface, and only the cards take pointer events (the gaps pass orbit, zoom and picking to the canvas). They run from under the top bar (56 px) to 12 px above the bottom, 12 px from the right edge, and scroll when taller. The room settings and the "Loading…" message sit on a card surface.
- **Motion** (14.4): opening a room slides the floor widgets out (toward the right, owner; widgets placed on the left leave by the left edge so they never cross the room cards) and slides the room cards in from their side (from the right; from below for the sheet); closing reverses both, and opening another room mid-slide turns it round. The slides use the camera's inset spring (critically damped, 8 rad/s) as a CSS `linear()` easing over 1 s (`ha-viewer/three/springs.ts`; a cubic fallback where `linear()` is missing), so they start and settle with the camera move; reduced motion turns them off. The last room's cards stay mounted while they slide away.
- **Controls** (14.4): while a room is open the pencil (Edit mode) is hidden and the top bar holds, styled like it, the **gear** (on: the room settings replace the cards) and **close**; the cards start below them. The panel has no header any more.
- **No tab: full-screen room** (15.6, owner 2026-11-18): a room with no tab (none chosen and none matching, or the dashboard could not be read) shows no message and no card area. It still opens (camera focus, cutaway, gear and close in the top bar), but its frame insets are zero, so it is framed in the real centre of the whole screen and the backdrop follows (14.5). A read error or missing connection is a console warning only. The hint to choose a tab is in Settings only (the room's **Tab** field says "No tab is set ... opens full-screen, without cards"). The gear still works: its Room position and Sweep corners surface appears in the usual cards place (over the house, insets unchanged) only while the gear is open. The tabs are read when a room opens (cached per dashboard, read again in the background for the next opening), so adding a tab in Settings or in HA switches the room to the card layout on its next opening. Rule and insets: `roomHasTab` (`dashboardViews.ts`), `roomFrameInsets` (`roomInsets.ts`); checked by `npm run ha:conditions`.
- **Title** (14.4): hidden by default; the room's **Show room title** checkbox in Settings (beside Tab and Columns) shows the room's name above its cards.

**Camera moves** (owner, 2026-11-16: the fixed 700 ms cubic in-out looked robotic): the pan, turn, zoom, and frame insets (the space the room cards or floor widgets take) each follow a critically damped spring toward their goal (stiffness 7, 6.5, 5.5, and 8 rad/s; about 0.8 s to settle), so the pan leads and the zoom settles last. A new goal mid-move (tapping another room) keeps the current speed instead of starting from rest; grabbing the view stops the move. Frame-rate independent (steps of at most 8 ms).

**Picking** (Phase 8.1, `ha-viewer/three/roomPicking.ts`): a tap runs an ordered pick pipeline, and the first stage that claims it wins: bubble (8.5) → light → object action (8.3) → room. Bubbles are HTML elements over the canvas and take their own pointer events ([bubbles](#bubbles)); the canvas stages are light, object, and room. The object stage takes the nearest surface when it belongs to an object that takes gestures (outside Edit mode: an action, or the AC default; in Edit mode every object); any other object is looked past, so its room answers. Doors and windows answer in the same stage by their own instance geometry (`instance:<id>`: leaf, sash, frame, glass, blinds; never the wall around them): outside Edit mode when they take gestures (10.1), in Edit mode always (9.7). The light stage takes the nearest drawn surface when it belongs to a light's fixture (tap, hold, and double-tap gestures as before). The room stage takes the nearest surface's room: a floor, carpet, object, door, or window in that room's `area:<id>` group, or a wall's **interior** face (RealAllWalls face provenance, `faceOfTriangle`); anything else (an exterior face, a wall end or top, empty space) goes to the **room hit volumes**: per area its floor shape extruded from the floor to its highest wall + 50 mm (2500 mm without walls), analytic prisms in plan mm (`ha-viewer/three/roomVolumes.ts`, no meshes, nothing drawn), and the volume the pointer ray enters first wins. So a tap above a far room, on its walls, or on its floor opens it. While a room is open, surfaces the cutaway removed or faded are looked through.

**Smart focus** (Phase 8.2, owner decision Q5, `ha-viewer/three/roomFocus.ts`): a room without a saved position is framed as before (target over its floor centre at 1.2 m, distance fitted to its bounds and the free part of the screen), but the angle is chosen: 8 azimuths 45° apart, starting at the current one, × 3 elevations (the current one, +15°, +30°, within the orbit limits). Each candidate is scored by the share of about 36 floor samples (a grid over the room's floor shape, 100 mm up, not under its walls) that the eye sees past every occluder: all wall bands (2.5D prisms) and the boxes of other rooms' objects; the room's own contents never block. The best share wins, but any candidate within 0.08 of it wins instead when it turns less (azimuth turn + 1.5 × elevation change), so a room that is already visible keeps the current angle. The camera then flies there with the spring move. A saved room position always wins. Implementation conventions; `npm run viewer:focus` checks the math on fixed scenes.

**Cutaway** (Phase 8.2a, `ha-viewer/three/roomCutaway.ts`): while a room is open, what stands between the camera and the room gets out of the way, with a saved position too; closing the room restores the house. The owner picked **A (fade)** on 2026-11-17 and replaced it with **C (dithered fade)** on 2026-11-20 (Phase 21.3: much faster, no visible difference while working); C is the only behaviour, A its fallback, and the setting is gone (variant B's code stays unused). The variants:

- **A. Fade** (C's fallback; the default until 2026-11-20): the builder's isolation fades every other room (walls, floors, carpets, objects, light fixtures) to the dimmed level (opacity 0.1); the room's own walls whose centre lies within ±70° of the camera's side, and the doors and windows on them, fade to 0.25 and follow the camera as it orbits. The room's walls are drawn as their own layer while it is open (the builder's isolation approximation: merges with neighbours are not shown), cut also by the neighbours' doors and windows in its walls. **Shared-wall openings** (Phase 15.7, owner report: a corridor hid a neighbouring room's door): a door or window stored on another room's wall counts as the open room's own when that wall runs along the open room's boundary, whichever area stores it: it is drawn clear and pickable (by its own instance geometry, 10.1) and fades with the open room's wall there when that wall is on the camera's side, like the room's own doors; the neighbour's furniture, lights, and wall band stay dimmed. The rule is geometric and shared with the builder's Room Editor ([floor builder](../builder/screens/floor-builder.md#editing-focus-in-room-editor)): the opening's cut footprint (its wall's span across the merged parallel wall thickness + 0.5 mm) holds a parallel edge of the open room's floor outline, within 1 mm more (`shared/geometry/sharedOpenings.ts`); a door there stays in its own room's group, so a tap on it outside its gestures still opens that room. Checked by `npm run geometry:walls` (synthetic pair) and `npm run viewer:focus` (generic shared-wall invariants on the demo house "Demo: City apartment").
- **C. Dithered fade** (default; Phase 21.3, `ha-viewer/three/ditherFade.ts`): A's look without its cost. Every material of the view carries one shader test (patched when it first appears, so it compiles with the house behind the loading bar); opening, closing, and orbiting a room change shared uniforms only: no isolation layers, no faded material copies, no shadow redraw, static batches kept. Per fragment, on the ground plane: inside the room's outline it is drawn as is; within the room's wall thickness outside the outline (its walls, their doors and windows, so also a neighbour's door in a shared wall) it is drawn as is, or at the faded level when the nearest outline edge lies on the camera's side (±70° of the camera's direction from the room centre, per edge, followed as the camera orbits; a wall fragment on the outline itself counts as the wall); everything else is at the dimmed level. A level is the fraction of pixels kept in a fixed Bayer 4×4 pattern (dimmed 0.1, faded 0.25, as A's opacities); the pattern is stable while the camera rests. Picking looks through a fragment kept at less than half. A room without an outline (walls off) or with more than 48 outline edges falls back to A. Shadows are unchanged (a thinned wall still casts, as A's faded walls did).
- **B. Reverse dome** (owner idea): a ring around the whole house (its bounding circle + 1 m) at the highest wall + 0.3 m, its centre pulled down to the room's floor centre (+ 5 cm), forms a funnel; for a point at distance r from that centre and s from it to the ring, the surface is at `apex + (top − apex) · (r / s)^2`. Every mesh material gets a shader test (`onBeforeCompile`) that discards fragments above the surface, with a 0.3 m dithered soft edge; nothing outside the ring is cut, and the room's own contents inside its plan box are never cut (its walls are). From a low camera the ring is shifted toward the camera until the line of sight to the room clears the wall tops (× 1.25). Parameters: `defaultFunnelParams` in `ha-viewer/three/cutawayFunnel.ts` (ring margin, curve, soft edge, reach, floor clearance, roof margin). Cut walls still cast their shadows.
- **Off:** nothing changes (the room is only framed).

- **Dashboard:** one HA dashboard created and edited in HA; each room has a tab (view). The tab's layout is drawn the way HA draws it: a sections view as sections in as many columns as the panel width gives, up to the view's `max_columns` (each section's `column_span`) with each card spanning its `grid_options.columns` of the section's 12 and at least `grid_options.rows` rows; a masonry view as that many balanced columns; a panel view as its single card. Cards are created with `loadCardHelpers().createCardElement` and receive every new `hass`. The dashboard is read over the websocket with `lovelace/config`; the default dashboard has URL path `lovelace` and is requested with a null path.
- **Matching:** a room opens the tab chosen for it; a room without a choice matches a tab by `path`, then `title`, ignoring case and separators. A room with no tab opens full-screen (see below); a dashboard read error is treated the same.
- **Room settings:** the dashboard (`lovelace/dashboards/list`, admin only; a typed URL path is the fallback) is set in Settings → **House**; each room's **Tab** and, below it, **Columns** (the panel width, 1 or 2 section columns, 1 by default; owner 2026-11-17: a room setting, not a house one) are at the top of the room's editor in Settings (drafts saved with Settings' Save). The gear (in the top bar while the room is open, 14.4) keeps what needs the 3D view: **Room position** and, for a room with a presence entity, **Sweep corners**; both swap the cards for them in the same place and save at once.
- **Room position:** while the gear is open the 3D view stays interactive (orbit, zoom, and pan with the chosen [navigation](#houseviewer)). **Use this view as the room position** saves the camera; opening the room later flies to it. **Automatic** removes it, and the room is framed to fit again, at the angle smart focus chooses.
- **Storage:** `homeAssistant.dashboard = { urlPath, areaTabs, areaViews, areaColumns, areaTitles?, floorTabs?, floorColumns?, floorPositions?, navigation?, mainViews? }` (`navigation`: [the viewer's navigation](#houseviewer), 14.6; `mainViews`: [main view](#floors-and-the-whole-house), 16.1) in preferences (the floor maps: [floor widgets](#floor-widgets)), where `areaTabs[houseId][areaId]` is a tab's `path` (else `title`), `areaColumns[houseId][areaId]` is 1 or 2 (absent = 1; the earlier house-wide `panelColumns` is dropped on read), `areaTitles[houseId][areaId]` is `true` for a room whose title shows (absent = hidden; the map is optional, so settings stored before 14.4 stay valid, the defaults hold it empty, the integration's `SnapshotDashboard` carries it optionally and the HA store copies it on the one-time import like the room tabs) and `areaViews[houseId][areaId]` is `{ target: { x, y, h } (plan mm), distance (m), azimuth, polar (rad) }`. `PATCH /api/preferences` with `homeAssistant.dashboard` replaces it whole. Schema: [`shared/domain/schemas/homeAssistant.ts`](../../shared/domain/schemas/homeAssistant.ts).

## Floor widgets

Owner requirement (2026-11-18, Phase 13.7; **implemented**, `ha-viewer/floorWidgets.ts`, `ha-viewer/floorWidgetSetting.ts`). A floor can show a dashboard tab's cards beside the house, drawn over the 3D render with no panel background. This reuses the room-card drawing ([room cards](#room-cards): `readViews`, `buildLayout`, HA's card factory in `ha-viewer/dashboardCards.ts`, every new `hass` fed to the cards) and adds a level to the Settings tree.

- **Settings tree:** House, then **Floor** (the shown floor's name, "Floor widgets and presence"; its editor also holds the floor's [presence gate](#presence-and-intrusion)), then its rooms one step in, always, also for a one-floor house ([bindings: editor](bindings.md#editor)). The viewer shows one floor at a time (or, for a multi-floor house, the [whole house](#floors-and-the-whole-house), which has no Floor level in the tree and shows no widgets); a house-level widget tab is not part of 16.1. A floor's editor has **Widget tab** (a tab of the house's dashboard; **None** by default, so a floor shows no widgets until one is chosen), **Position** and **Columns**, drafts saved with Settings' Save. Choosing another dashboard drops the house's floor tabs, like its room tabs.
- **Position and columns:** **Left** and **Right** allow 1 or 2 section columns; **Top** and **Bottom** allow 1 to 4. Changing the position clamps the columns to the new maximum. Without a stored position the widgets sit on the right (implementation convention, like the room panel). The widget area is the width of its columns (340 px each, 16 px apart; never wider than the screen less 24 px): beside the house it runs from under the top bar (56 px; on the left from 12 px, since the top bar's controls are at the right, owner 2026-11-18) to 12 px above the bottom, 12 px from the side; above or below it is centred, at most 40 % of the height, and scrolls when the cards are taller.
- **Framing:** the house is fitted into the space the cards leave, as the room panel does: the viewer frames the whole floor into the screen less the widget area's box plus an 8 px gap (`HouseViewer.setFloorInsets`, at most 70 % of the width or 60 % of the height), and the view glides there with the same springs as a room move when the widgets appear, resize, or move.
- **No background:** the widget area is transparent; each card keeps the surface HA draws for it. A background-colour setting may be added later if readability needs it.
- **Pointer events:** only the cards take them; the area and the gaps between cards pass orbit, pan, zoom, and picking through to the canvas, as bubbles do.
- **Room taps:** opening a room slides the floor widgets away (14.4, [room cards: motion](#room-cards)) and the house is framed beside the room cards; closing the room slides the widgets back and the floor is framed into their space again.
- **Floors:** the widgets belong to the shown floor and change with it.
- **Narrow screens (under 700 px):** the widgets go below the house, the full width less 24 px and at most half the height, in at most 2 columns, whatever the position.
- **Missing tab:** a chosen tab that is no longer in the dashboard shows no widgets (the floor editor says so).
- **Storage:** beside `areaTabs` and `areaColumns` in `homeAssistant.dashboard`, keyed by house and floor ID: `floorTabs[houseId][floorId]` (a tab's `path`, else `title`; absent: no widgets), `floorColumns[houseId][floorId]` (1–4; absent: 1) and `floorPositions[houseId][floorId]` (`left`, `right`, `top`, `bottom`; absent: `right`). The three maps are optional, so settings stored before 13.7 stay valid; the defaults hold them empty. Installation-global; never in `house.json`. Schema: `HaDashboard` in [`shared/domain/schemas/homeAssistant.ts`](../../shared/domain/schemas/homeAssistant.ts); the integration's `SnapshotDashboard` (`shared/contracts/homeplanIntegration.ts`) carries them optionally, and the HA store copies them on the one-time import like the room tabs.

## Presence and intrusion

Owner request K18, decision Q6 (2026-11-16; Phase 8.6): a room shows presence or an intrusion as pulsing red light cones sweeping from chosen corners and a faint red tint. The setting (entity, condition, corners) is part of the room's binding: [bindings: presence](bindings.md#presence).

- **Setting** (Settings, the room's editor, **Presence and intrusion**, `ha-viewer/presenceSetting.ts`): the entity (`ha-form` `entity` selector limited to `binary_sensor` and `alarm_control_panel`; a plain select outside HA), **Active when** (the condition editor; empty means the state is `on` or `triggered`), and a live **Now: active / clear** badge, with a line saying which corners sweep. Changes are part of the Settings draft (Phase 10.9) and are saved with its Save. The corners themselves are chosen with the open room's gear (owner 2026-11-17: they need the 3D view). The section's title and description use exactly the room editor's section heading style (owner, 2026-11-18: before, the element drew its own smaller, grey heading).
- **Floor gate** (owner, 2026-11-18; Settings, the floor's editor, **Presence and intrusion**): a condition that must hold for any room of that floor to sweep, for example "the alarm is armed" (`alarm_control_panel.*` in an `armed_*` state); any condition of the editor works, and the hint suggests the alarm example. While it does not hold, no room of the floor sweeps or tints, whatever its own entity says; absent, every room follows its own setting. Stored in the house's bindings as `floors[floorId].presenceWhen`, installation-global ([bindings: floor presence gate](bindings.md#floor-presence-gate)); `viewerScreen.ts` passes only the allowed rooms to the sweeps (`intrusionRooms`, `bindingEvaluator.ts`), and arming or disarming updates them live.
- **Choosing corners:** with the room open, gear (top bar) → **Sweep corners** (shown when the room has a presence entity) → **Choose corners** turns on corner picking: a marker sits at every corner of its outline, at sensor height (red: sweeps; white: does not), and a pill reads "Tap near a corner of … to add or remove it" with **Done**. A tap within 36 px of a marker toggles it (at most 8) in the draft; nothing else runs while picking, and the Edit bar buttons are hidden. **Done** (or closing the room) saves the changed corners at once, like the room position. **Default corners** returns to the default two (saved at once): the two corners farthest from the room's doors (openings whose bottom is at most 50 mm), or the two farthest apart in a room without doors. Corners are stored in the area's own frame and match the nearest corner of the current outline within 300 mm, so moving or turning the area keeps them and an edited outline drops only the corners that are gone.
- **Sensors:** each chosen corner gets a sensor pushed out of the wall bands along the corner's inward bisector plus 120 mm, 250 mm below the room's highest wall top (at most 2.6 m), shown as a small red dot. Its cone (half-angle 15°, soft outer third) points along the bisector and down to meet the floor half the room's diagonal away (1.5–5 m), swings ±35° around it (one side to the other in 4 s, each sensor at its own phase), and pulses (55–100 % over 1.6 s).
- **Drawing (an overlay, not a light):** `ha-viewer/three/intrusionSweep.ts` adds no three.js light and patches no house material, so the shadow budget, the lighting (8.9), and the cutaway's material patches are untouched. Every drawn mesh of the room (floor, carpets, objects, doors, windows, fixtures) and every wall layer of the floor get a twin that shares its geometry and world matrix, with one small shader: the red of every cone that holds the fragment (soft edge, distance falloff, a Lambert term toward the sensor) plus the tint, masked to the room's outline + 40 mm (which takes in the walls' interior faces; faces turned away from the room get nothing). Twins draw after the house with a less-or-equal depth test pulled forward by a polygon offset, no depth writes, blended `src + dst · (1 − a)`, so the red reads on dark and on white surfaces. Faded surfaces (cutaway A, isolation) get no twin face; the reverse dome (B) cuts twins with the house's own uniforms and formula (`funnelGlsl`, shared by reference). Twins live on the effects layer outside the plan root: never picked, no shadows, not in exports, hidden from the glass reflection.
- **Frames:** while at least one room is active, a timer asks for view-only frames at 24 fps; when every presence clears, the timer stops and nothing more is drawn for it. Sweep frames never redraw the shadow maps. `prefers-reduced-motion`: the cones stand still at their resting direction and do not pulse; one frame per change.
- **Shield bubble (hook for 8.5):** room bubbles (8.5) can add a presence bubble with `mdi:shield-alert`, shown while `BindingEvaluator.presenceActive(areaId)` holds; nothing of it is drawn by 8.6.
