# Working in this project

The workspace contains the specification and the MVP application (`src/` SPA, `server/` Fastify backend, `shared/` domain/geometry/contracts; see [README.md](README.md) for commands). Start with [spec/README.md](spec/README.md), then [MVP scope](spec/product/mvp-scope.md) and the [decision register](spec/decisions.md). Every product decision is resolved or deferred; implementation conventions (tolerances, timings, limits) are chosen and documented during implementation. Preserve the distinction between owner requirements, resolved decisions (owner or review inference), implementation conventions, and post-MVP notes.

For application structure, read [frontend architecture](spec/architecture/frontend-architecture.md) and [state/resource access](spec/architecture/state-and-data.md), then the owning feature specification. Proposed source paths and client methods are not evidence of existing files or endpoints: inspect actual source before importing or calling them.

D13 is resolved. The selected MVP stack is React/TypeScript + Vite, Node/Fastify, React Router Data Mode, Zustand vanilla editor/session stores, typed fetch resource clients, Tailwind/data selectors in `.tw.css`, and a React-hosted Three.js runtime. Schemas are authored with TypeBox; accessible UI behavior comes from React Aria Components; tooling is npm + ESLint + Prettier; no automated test stack yet. Do not reopen Next.js/Fiber or add TanStack Query as baseline dependencies. Domain commands/geometry remain separate from React, stores, transport, and filesystem repositories. Use the documented responsibility map rather than introducing another parallel convention.

Every form is built with the schema-driven form builder (`SchemaForm`; popups via `Popup`/`FormPopup`), never hand-coded; see [forms and popups](spec/design-system/README.md#8-forms-and-popups). Backend routes are owned by [the API spec](spec/architecture/api.md); house assets (images, templates) are server-owned and `house.json` references them by ID. Shared components follow [design-system conventions](spec/design-system/README.md), including the fixed component file layout (imports → props type → exported component; see [file layout](spec/design-system/README.md#file-layout-imports-props-component)), no shortcuts or workarounds (`any`, casts, `@ts-ignore`, `eslint-disable`), one named typed arrow-function component per file and data-attribute styling in `.tw.css`. Document each implemented shared component with real examples, props, and matching View source content under the required unlisted `/ds` application route, as specified in [the workbench](spec/design-system/workbench.md).

When changing a shared contract, update its owning spec and affected references/examples together. Keep a single authoritative model and explicit revision-aware saves. Verify documentation links/JSON for documentation changes. For code, `npm run lint` and `npm run typecheck` must pass with no suppressions; `npm run geometry:walls` checks the wall-merge scenarios and `npm run templates:build` regenerates and validates the built-in templates.

MVP is builder-only, in two phases (see MVP scope). Floor shapes and walls are authored guides; RealFloor, RealWall, and RealAllWalls are derived and never persisted. There are no wall-driven floors. Geometric commands use click–lock–type–commit input (D16). Object templates are glTF 2.0 with Homeplan metadata in `extras` (D17); do not introduce a custom asset format. Object properties are defined by one JSON Schema per type with `x-homeplan` annotations and edited through the schema-driven property panel (D18); do not hand-code per-type property forms. Saves send full JSON documents; explicit Save creates a per-house Git revision (D09). All other Home Assistant work is post-MVP, including cards, scene/image publishing, and HA-specific authoring UI in the builder. Future HA specs live only under `spec/home-assistant/`; do not treat them as MVP acceptance gates. Exception: the [HA viewer MVP](spec/home-assistant/viewer-mvp.md) (D23) with its [bindings](spec/home-assistant/bindings.md) (D25) and [production integration](spec/home-assistant/production-integration.md) (D27, `custom_components/homeplan/`), and the [Home Assistant app packaging](spec/home-assistant/publishing.md#app-packaging-and-ingress) (`config.yaml`, `Dockerfile`, `repository.yaml`, `DOCS.md`) are active work. The viewer lives in `ha-viewer/`, is built with Lit + Lit `css` (Home Assistant theme variables) + framework-free Three.js, and imports only `shared/` and the framework-free `src/renderer/`; the React/Tailwind/React Aria/`SchemaForm`/`/ds` rules do not apply there, and it must not import anything else from `src/`. Keep `src/renderer/` free of React and stores so both front ends can use it. Local model editing, saving, rendering, and PNG exports remain independent.

D12 is resolved: no application users, accounts, profiles, roles, or per-user ownership. All durable data/preferences are installation-global. Do not introduce a dummy local profile, user-scoped preference API, or speculative authentication/user abstraction. A future user layer is a separate design; ordinary resource/schema/path validation remains required.

When an editor interaction decision is open (tools, snapping, handles, selection, camera), follow Trimble SketchUp's behavior unless a spec says otherwise (owner instruction).
